# 游戏开发术语与流程手册｜ChatGPT 写给五月七日的指导笔记 001

**撰写：ChatGPT · 中英日术语与资料核对：2026-10-15**

**001 术语与流程** · [002 软件与制作能力](posts-2026-umwelt-game-development-handbook-002.html)

游戏开发从**概念、规则、原型和制作样板**开始，经过**程序、资源与内容生产**，再进入**测试、发布和维护**。本篇按这些工作的位置整理术语：查一个词时，可以同时知道它解决什么问题、与哪些工作相连、完成后交给谁。可从目录定位阶段，也可用页面查找（⌘F／Ctrl+F）搜索中、英、日名称。

表中的日文采用常见写法或便于检索的对应说法；团队和软件可能使用不同译名，缩写通常保留英文。[16](#ref-16), [17](#ref-17) 阶段会反复往返，美术、程序、音频、测试也会并行。案例先交代玩法，再比较同一问题的不同解法；开发事实附来源，对设计效果和工作量的判断属于本文分析。

## 01｜概念与立项：确定作品及其边界

概念阶段把题材转成可制作的体验。“关于海上旅行”是主题；“玩家在渡轮上观察邻座、选择回应，并从动作理解关系变化”进一步说明了玩家行为。平台、输入、时长、人数和画面形式会决定后面的工作量。

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 概念 | Concept | コンセプト | 对作品体验与形式的概括；是规则、美术和规模取舍的起点 |
| 高概念 | High Concept | ハイコンセプト | 能用很短说明传达的主要吸引力，例如“通过移动文字改变世界规则” |
| 提案／企划案 | Pitch | ピッチ／企画提案 | 向合作者或发行方说明体验、受众、可行性与所需支持；常以演示和简报呈现 |
| 目标受众 | Target Audience | ターゲット層 | 优先服务的玩家；影响操作门槛、信息量、设备和内容表达 |
| 独特卖点 | USP — Unique Selling Proposition | 独自のセールスポイント | 与其他选择相比值得关注的特点；需要由实际体验支持 |
| 设计支柱 | Design Pillars | デザインピラー | 少数持续用于取舍的原则，如“观察先于解释”“失败后迅速重试” |
| 游戏类型 | Genre | ゲームジャンル | 对常见玩法结构的分类；动作、解谜、经营等可混合，标签本身不能代替规则说明 |
| 平台 | Platform | プラットフォーム | 成品运行和分发的环境，如桌面、浏览器、手机、主机；会影响输入、性能和发布 |
| 范围 | Scope | スコープ／制作範囲 | 本次承诺的功能、内容、平台和品质；应尽量写成可核对数量 |
| 范围膨胀 | Scope Creep | スコープクリープ | 新需求不断加入而预算、期限没有相应调整；小功能也可能产生大量组合工作 |
| 约束 | Constraint | 制約 | 时间、人力、设备、许可和艺术方向等边界；约束直接参与设计 |
| 风险 | Risk | リスク | 可能影响交付的不确定事项；按发生可能性与影响排序，安排验证 |
| 可行性 | Feasibility | 実現可能性 | 技术能否实现、制作资源是否足够、长期是否可承担；三个问题分别检查 |
| 立项放行 | Greenlight | 企画承認／グリーンライト | 根据现有材料决定继续投入；可以只批准下一段验证工作 |

### 同一个问题：场景有限，怎样仍有足够的内容

| 游戏与玩家行为 | 具体做法 | 为什么能形成内容；结果与代价 |
| --- | --- | --- |
| [《Papers, Please》](https://papersplea.se/)：玩家坐在边检窗口，核对证件并决定是否放行 | 地点基本固定，变化来自每日规则、证件矛盾、来访者请求和时间压力 | 同一组检查动作遇到不同条件，就会产生不同判断。场景制作较集中，规则组合、文字和例外测试却会增加 |
| [《A Short Hike》](https://ashorthike.com/)：小鸟在岛上徒步、攀爬和滑翔，目标是登上山顶 | 把收集、相遇和路线选择放进紧凑空间；同一地点可步行经过，也可从高处滑翔返回 | 空间通过不同移动方式反复使用。作者在初版四个月期限内对美术、关卡和写作作出取舍；这种办法要求路线与移动本身有趣。[1](#ref-1) |
| [《Hades》](https://www.supergiantgames.com/games/hades/)：主角反复尝试逃出冥界，失败后回到家中 | 战斗组合与房间反复出现，角色关系和故事在多次尝试之间继续推进 | 重复挑战与长期变化并存。可重复游玩增加内容寿命，同时需要更多平衡、条件对白与状态检查。[2](#ref-2) |

三者分别把变化放在**规则与来访者、空间使用方式、多轮战斗与故事状态**里。范围不能只数地图；还要数动作、文本、条件和组合。下一步的规则设计，就是把这些变化写成可以实现的关系。

## 02｜玩法与规则：把体验转成可观察的关系

一项操作需要交代触发条件、当前前提、状态变化、反馈和结束方式。“点击杯子”只是输入；点击后是否抬杯、何时出现对白、连续点击会怎样，才是完整规则。

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 玩法 | Gameplay | ゲームプレイ | 玩家实际操作、判断和得到反馈的整体过程 |
| 机制 | Mechanic | メカニクス／ゲームの仕組み | 一项操作与规则的关系，如消耗体力攀爬、移动文字改变属性 |
| 核心循环 | Core Loop | コアループ | 反复连接行动、反馈和下一次选择的结构；一次循环可短至几秒，也可跨一个游戏日 |
| 外层循环 | Meta Loop | メタループ | 多次核心循环之间的长期安排，如解锁装备、扩建基地和推进关系 |
| 目标／胜败条件 | Goal / Win & Lose Conditions | 目標／勝利・敗北条件 | 玩家努力达到的状态及本轮何时结束；开放体验也可以有局部目标 |
| 反馈 | Feedback | フィードバック | 让玩家知道行动结果的信息，包括画面、声音、震动、文字和状态变化 |
| 可供性／操作线索 | Affordance / Signifier | アフォーダンス／シグニファイア | 前者指可以做什么，后者指提示玩家如何操作的线索；发光轮廓可能是可点击的提示 |
| 玩家能动性 | Agency | エージェンシー／主体性 | 玩家能作出有影响的选择，并理解行动与结果的关系 |
| 进程／成长 | Progression | プログレッション／進行・成長 | 能力、资源、剧情或知识怎样随游玩变化；进步不必表现为等级 |
| 奖励 | Reward | 報酬／リワード | 行动后的有价值结果，如新能力、信息、情感回应或资源 |
| 风险与回报 | Risk–Reward | リスクとリターン | 可能损失与预期收益的关系；决定冒险是否值得 |
| 游戏经济 | Game Economy | ゲーム内経済 | 资源怎样产生、交换、消耗和积累；包括货币，也包括体力、时间等 |
| 资源来源／回收口 | Source / Sink | 供給源／消費先 | 资源进入和离开系统的渠道；只增加供给而缺少消耗，可能持续通胀 |
| 平衡／调参 | Balancing / Tuning | バランス調整／パラメータ調整 | 调整规则和数值，使选择、压力与节奏接近目标；不等于所有选项完全一样 |
| 难度曲线 | Difficulty Curve | 難易度曲線 | 挑战随进程的变化；应结合玩家已学会的能力判断 |
| 随机数／种子 | Random Number Generator — RNG / Seed | 乱数／シード値 | 随机过程及其起点；在相同算法和条件下，固定种子有助于复现生成结果 |
| 程序化生成 | PCG — Procedural Content Generation | プロシージャル生成／自動生成 | 用规则和数据生成关卡等内容；仍需设计约束、筛选与测试 |
| 涌现 | Emergence | 創発 | 多个简单规则组合后出现未逐一写死的情况；组合越自由，边界测试越重要 |
| 游戏手感 | Game Feel | 操作感／ゲームフィール | 输入、运动、碰撞、相机与反馈共同形成的操作感受 |
| 容错窗口 | Grace Window | 猶予時間／入力猶予 | 在时间或位置上接受接近玩家意图的操作，减少细小误差带来的失败 |
| 输入缓冲 | Input Buffer | 入力バッファ／先行入力 | 暂存过早的输入，在允许执行时使用；如落地前按跳跃，落地时起跳 |
| 土狼时间／离边宽限 | Coyote Time | コヨーテタイム | 离开平台边缘后的短暂时间内仍允许跳跃，是动作容错的一种 |
| 冷却／无敌帧 | Cooldown / Invincibility Frames | クールダウン／無敵時間 | 再次使用能力前的等待／暂时不受特定伤害的时间；需与动画、输入和反馈对应 |
| 检定／概率 | Check / Probability | 判定／確率 | 按条件、数值或随机结果决定行动是否成立；需要让玩家理解可预期程度 |
| 元游戏／主流打法 | Metagame / Meta | メタゲーム／メタ | 游戏规则之外或长期演化的策略选择，如依据常见对手调整配置；与长期成长循环 Meta Loop 区分 |

### 同一个问题：怎样让玩家愿意再做一轮

| 游戏与一轮行为 | 做法及其作用 | 最后形成的差异 |
| --- | --- | --- |
| [《星露谷物语》](https://www.stardewvalley.net/)：安排一天，种植、采集或交往，再结束当天 | 作物和建筑需要跨日发展，每天的时间与体力有限；今天的选择会改变明天的资源 | 动力来自积累和安排。增加内容时，要检查季节、日程、价格和人物条件 |
| [《Celeste》](https://www.celestegame.com/)：控制少女在短小房间内跳跃、攀爬和冲刺 | 障碍让玩家不断修正路线与按键时机；失败后很快重试。作者还用输入缓冲和离边宽限贴近玩家意图。[10](#ref-10) | 动力来自“这次更接近成功”。关键工作是动作规则、房间布局和失败成本 |
| [《Return of the Obra Dinn》](https://obradinn.com/)：登船查看死亡现场，推断船员身份和命运 | 同一现场里的服装、站位、声音等信息可以和其他现场互相印证 | 进展主要是理解增加。制作重点转向线索一致性、证据分配和推理反馈 |
| [《Outer Wilds》](https://www.mobiusdigitalgames.com/outer-wilds.html)：驾驶飞船探索处于时间循环中的太阳系 | 行星随时间改变，某次探索得到的信息能改变下一次出发地点与时机 | 玩家带着知识重新规划。比起增加装备数值，更需要检查信息是否能指向新行动。[19](#ref-19) |

这几种循环分别依靠**积累、熟练、推理、发现**。解释核心循环时，必须把“重复什么”与“重复以后改变什么”一起写清。

<a id="phase-2"></a>

## 03｜前期制作与计划：约定谁做、怎样接、何时检查

前期制作把概念整理成规则、资源规格和生产方法。文档先支持眼前的验证，再随决定更新；未确定的部分明确列为待验证，避免多人各自补全假设。

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 前期制作 | Pre-production | プリプロダクション | 确定设计、技术、美术方向与生产方法，为大规模制作降低不确定性 |
| 游戏设计文档 | GDD — Game Design Document | ゲームデザインドキュメント／仕様書 | 记录玩法、内容、规则和体验目标；小项目可以拆成少量专题文档 |
| 技术设计文档 | TDD — Technical Design Document | 技術設計書 | 记录系统、数据、依赖与实现安排；TDD 在测试语境另有含义 |
| 美术规范 | Art Bible / Style Guide | アートバイブル／スタイルガイド | 统一形状、色彩、光照、比例及资源规格；供不同作者保持一致 |
| 制作管线 | Pipeline | パイプライン | 源工程经过导出、转换、导入和检查，最终进入成品的步骤 |
| 数据约定 | Data Contract | データ仕様／インターフェース仕様 | 规定字段、类型、单位、编号及缺失值含义；避免两端各自解释 |
| 资源清单 | Asset List | アセットリスト | 记录所需图像、模型、声音、文本与状态；与功能任务相互对应 |
| 里程碑 | Milestone | マイルストーン | 有明确成果和判断条件的检查点，如“完成一段目标品质体验” |
| 待办列表 | Backlog | バックログ | 尚未完成的需求、任务和问题；记录想法不等于承诺全部制作 |
| 迭代周期 | Sprint / Iteration | スプリント／イテレーション | 在限定周期内完成一组工作并检查；Sprint 是特定方法中的周期安排 |
| 依赖 | Dependency | 依存関係 | 某项工作需要的前提；例如角色比例会影响动画、碰撞和镜头 |
| 关键路径 | Critical Path | クリティカルパス | 决定整体最早完成时间的一组依赖任务；这些任务延误会推迟交付 |
| 预留 | Contingency / Buffer | 予備費／バッファ | 为已知不确定性预留预算或时间；应与具体风险联系 |
| 完成标准 | Definition of Done — DoD | 完了の定義 | 团队约定“做完”包含哪些检查与文件；避免只在作者机器上成立 |
| 验收条件 | Acceptance Criteria | 受け入れ条件 | 某项任务可被接受的具体结果；如读档后仍保持已选对白分支 |
| 外包 | Outsourcing | 外注／アウトソーシング | 将部分制作交给外部作者；需要规格、源文件、许可、修改与验收安排 |

### 岗位名称与职责

| 中文 | English | 日本語 | 通常负责什么 |
| --- | --- | --- | --- |
| 制作人 | Producer | プロデューサー | 资源、预算、人员、进度和交付协调；公司间职责范围不同 |
| 总监／导演 | Director | ディレクター | 作品方向与主要创作决定，协调各专业形成一致体验 |
| 游戏设计师 | Game Designer | ゲームデザイナー／プランナー | 规则、操作、数值和体验结构；日本的“プランナー”常承担其中部分工作 |
| 关卡设计师 | Level Designer | レベルデザイナー | 路线、障碍、遭遇、引导与空间节奏 |
| 叙事设计师／编剧 | Narrative Designer / Writer | ナラティブデザイナー／シナリオライター | 前者侧重故事与交互系统的关系，后者侧重具体文本；职责可以重叠 |
| 程序员 | Programmer / Engineer | プログラマー／エンジニア | 实现运行系统、工具及各部分连接 |
| 美术师／动画师 | Artist / Animator | アーティスト／アニメーター | 制作视觉资源／动作与表演 |
| 技术美术 | Technical Artist — TA | テクニカルアーティスト | 衔接美术与运行要求，处理材质、绑定、工具和资源流程 |
| 作曲／声音设计 | Composer / Sound Designer | 作曲家／サウンドデザイナー | 音乐／声音素材、交互音频与声音表现 |
| QA／测试人员 | QA / Tester | QA／テスター | 设计检查、复现问题和提供质量信息；具体修复通常交回制作岗位 |

一人可以承担多个岗位。流程仍要保留**决定、制作、检查**三种职责：否则资源虽然完成了，却可能没有人确认它是否适合游戏。前期约定随后进入原型和制作样板，接受实际检验。

## 04｜原型与制作样板：验证体验，也验证生产能力

原型回答“这件事是否成立”；制作样板进一步回答“能否以目标品质持续完成”。两者可以使用同一个小项目，但要分别得到体验与生产的结论。

| 中文 | English | 日本語 | 含义与区别 |
| --- | --- | --- | --- |
| 原型 | Prototype | プロトタイプ／試作 | 用较小投入验证玩法、视觉或技术假设；可以保留，也可以完成验证后舍弃 |
| 纸面原型 | Paper Prototype | ペーパープロトタイプ | 用纸张、卡片等模拟规则或界面；适合先检查关系与信息，无法直接证明实时手感 |
| 概念验证 | Proof of Concept — PoC | 概念実証 | 侧重方案能否实现，如目标手机是否能加载某种资源；用法与原型可能交叉 |
| 灰盒／白盒 | Graybox / Whitebox | グレーボックス／ホワイトボックス | 用简单形状验证尺寸、移动和空间关系；名称不强制对应某种颜色 |
| 占位资源 | Placeholder | 仮素材／プレースホルダー | 暂时代替最终图片、模型、声音和文本；需要注明何时替换 |
| 限时验证 | Timebox | タイムボックス | 先限制投入，到期根据观察决定继续、改方向或停止 |
| 垂直切片 | Vertical Slice | バーティカルスライス | 小段内容贯通主要系统并接近成品品质，用来验证完整生产流程 |
| 水平切片 | Horizontal Slice | ホリゾンタルスライス | 较广地覆盖系统或流程，但每部分可能仍粗略；具体范围由团队约定 |
| 质量基准 | Quality Bar | 品質基準 | 可供后续资源对照的完成程度，如代表性场景、角色与声音样板 |
| 具备生产条件 | Production-ready | 本制作に移れる状態 | 方法、工具和规格足以支持重复产出；不能只凭一次漂亮演示判断 |
| 演示／试玩版 | Demo | デモ／体験版 | 描述供人体验的用途；可能来自原型或成品片段，成熟度另行说明 |
| 最小可行产品 | Minimum Viable Product — MVP | 実用最小限の製品／MVP | 用较小产品检验价值等假设；“可行”必须对应事先设定的验证目标 |
| 游戏创作活动 | Game Jam | ゲームジャム | 在限定时间与主题等条件下制作游戏；适合尝试规则，但不自动完成长期生产验证 |

### 同一个问题：正式美术之前，到底先做什么

- [《Splatoon》](https://www.nintendo.com/en-gb/Games/Wii-U-games/Splatoon-892510.html)让玩家喷墨争夺地面，并在自己的墨水里移动与隐藏。早期用黑白方块测试喷墨和地面占领；俯视时，方块会融进同色墨水，转成三维视角后却仍显眼，于是团队继续尝试伏低、潜入等方式，后来发展为鱿鱼形态。**这里先验证“涂地—隐藏—移动”的关系，角色造型跟着规则发展。**[4](#ref-4)
- [《Baba Is You》](https://www.hempuli.com/baba/)是推箱式解谜，地图里的文字也能推动。`WALL IS STOP` 让墙阻挡移动，把句子拆开就会改变规则。作者保留的 Game Jam 版本已经能让人尝试这种关系。**这里最先需要的是“文字变化确实改变世界”的可玩谜题**；更多关卡是在已经能操作的关系上扩展。[5](#ref-5)
- [《A Short Hike》](https://ashorthike.com/)要让玩家在小岛上自由游走并登顶。作者从新原型出发，在较短期限内共同调整移动、岛屿、美术与写作。**这类项目需要及早把移动与空间放在一起试**：一个动作单独顺畅，还不能说明整座岛是否值得探索。[1](#ref-1)

三者的验证对象分别是**规则之间的关系、可改写的规则、移动与空间体验**。原型据此选最少资源；切片再补上目标画面、声音、界面与存档。切片完成后做第二个同类场景，才能更可靠地估算复用和返工成本。

## 05｜程序与运行：输入怎样变成结果

程序把玩家输入、当前状态、规则和资源连接起来。例如按下“交谈”，先检查是否已经在对白中，再选择文本、显示角色动作，并记录需要长期保存的结果。具体语言和工具见 [002](posts-2026-umwelt-game-development-handbook-002.html#tools-03)。

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 游戏引擎 | Game Engine | ゲームエンジン | 提供图形、输入、音频、场景等基础能力，项目继续实现自己的规则 |
| 编辑器／运行时 | Editor / Runtime | エディター／ランタイム | 制作与调试界面／成品执行的程序部分；玩家通常无需安装制作编辑器 |
| 框架／程序库 | Framework / Library | フレームワーク／ライブラリ | 框架进一步组织程序结构，库提供可调用功能；具体边界依产品而异 |
| 脚本 | Script | スクリプト | 表达规则或制作自动化的程序；不是所有脚本都在玩家端运行 |
| 变量类型／数据结构 | Data Type / Data Structure | データ型／データ構造 | 数值、文字等值的类别／组织数据的方法；物品表、背包列表和地图关系会采用不同结构 |
| 函数／方法 | Function / Method | 関数／メソッド | 可调用的一组操作／与对象或类型关联的操作；参数是输入，返回值是结果 |
| 类／实体组件系统 | Class / Entity Component System — ECS | クラス／エンティティ・コンポーネント・システム | 类描述对象的数据与行为；ECS 将实体、组件数据与处理系统分开，是另一种组织方式 |
| 编译／解释 | Compilation / Interpretation | コンパイル／インタープリター実行 | 将代码转换为另一种可执行形式／由运行程序解释执行；实际环境可以混合采用 |
| 依赖包／插件 | Package / Plugin | パッケージ／プラグイン | 可复用的代码或资源单元／扩展宿主能力的组件；升级要核对接口和许可 |
| 游戏循环 | Game Loop | ゲームループ | 程序反复处理输入、更新状态并准备画面的执行过程；与“核心循环”的设计含义不同 |
| 帧／模拟步 | Frame / Tick | フレーム／ティック | 一次画面更新／一次逻辑模拟更新；两者频率可以不同 |
| 帧间隔 | Delta Time | デルタタイム／経過時間 | 两次更新的时间差；用于把每秒速度换算成当前更新的移动量 |
| 对象／组件 | Object / Component | オブジェクト／コンポーネント | 对象表示游戏中的事物，组件承担显示、碰撞等部分能力；组织方式随引擎而异 |
| 场景／节点 | Scene / Node | シーン／ノード | 组织对象与关系的单位；Godot、Unity 等对“场景”的具体定义不同 |
| 实例／预制体 | Instance / Prefab | インスタンス／プレハブ | 由定义创建的具体对象／可重复生成对象结构的模板；Prefab 常见于 Unity |
| 状态／变量 | State / Variable | 状態／変数 | 当前情况／保存某项值的名称；例如是否拿过钥匙、当前生命值 |
| 有限状态机 | Finite State Machine — FSM | 有限状態機械／ステートマシン | 用有限状态及转换组织行为，如待机→交谈→选择→结束 |
| 事件／回调 | Event / Callback | イベント／コールバック | 发生某件事的通知／相应时机调用的处理；常用于连接动画、界面与规则 |
| 接口／开发工具包 | Application Programming Interface — API / Software Development Kit — SDK | API／ソフトウェア開発キット | 软件调用的约定／接入某种能力的工具和组件集合 |
| 中间件 | Middleware | ミドルウェア | 提供音频、物理等专门运行能力，接入引擎或项目 |
| 序列化／存档 | Serialization / Save Data | シリアライズ／セーブデータ | 把状态转成可保存格式／保存需要延续的游玩情况；两者并非同义 |
| 稳定标识 | Stable ID | 永続的な識別子 | 在修改名称或顺序后仍能识别同一内容的编号；用于文本、资源和存档引用 |
| 缓存／对象池 | Cache / Object Pool | キャッシュ／オブジェクトプール | 复用计算或加载结果／复用已经创建的对象，以减少重复工作 |
| 异步加载 | Asynchronous Loading | 非同期ロード | 资源准备与其他工作交错进行；还需安排等待、失败和资源就绪后的行为 |
| 刚体／触发区域 | Rigid Body / Trigger | 剛体／トリガー | 参与物理运动与碰撞的对象／进入或离开时发出事件的区域；触发区域不一定阻挡移动 |
| 射线检测 | Raycast | レイキャスト | 沿指定方向查询命中物体，用于指向选择、落地检测或视线判断等 |
| 人工智能／非玩家角色 | Artificial Intelligence — AI / Non-player Character — NPC | 人工知能／ノンプレイヤーキャラクター | 游戏中用于感知和决策的方法／非玩家直接操控的角色；简单角色也可只用固定规则 |
| 确定性 | Determinism | 決定性 | 在相同起始条件和输入下得到相同结果；用于复现、回放和某些联机方案 |
| 客户端／服务端 | Client / Server | クライアント／サーバー | 玩家端／提供服务与协作的端；单机网页也可由服务器分发文件 |
| 权威状态 | Authoritative State | 権威を持つ状態／正とする状態 | 多端出现分歧时，以谁的判断为准；常由服务端承担，也有其他架构 |
| 同步／不同步 | Synchronization / Desync | 同期／同期ずれ | 各端保持约定状态一致／计算或数据出现分歧 |
| 延迟／预测／回滚同步 | Latency / Prediction / Rollback Netcode | 遅延／予測／ロールバック方式 | 信息到达需时间；预测先估计结果，回滚方案在收到实际输入后恢复并重算 |

### 同一个问题：“这次做过的事”需要记住多少

| 游戏与情境 | 哪些继续，哪些重置 | 对设计和实现的含义 |
| --- | --- | --- |
| [《Baba Is You》](https://www.hempuli.com/baba/)：推动文字后发现自己走错了 | 撤销让局部操作退回之前的状态，玩家可立即尝试别的排列 | 重点是能恢复当前谜题的操作过程；试验成本低，便于探索规则 |
| [《Hades》](https://www.supergiantgames.com/games/hades/)：一次逃脱挑战失败 | 本轮战斗配置与长期成长、人物关系分别处理；返回据点后再出发 | “当前这一轮”和“整个存档”需要不同状态范围；失败仍可以带来长期进展 |
| [《星露谷物语》](https://www.stardewvalley.net/)：结束一天后继续经营 | 农场、物品、日期和关系延续到之后的日子 | 状态之间相互关联，修改作物、时间或人物条件时需要检查已有进度 |

这些是玩法层面的状态比较，不据此推断作品的实际代码结构。实现时先决定需要保留的意义，再选存储方式。

[《Factorio》](https://www.factorio.com/)则提供了有开发记录的联机例子：玩家共同建设包含大量机器的工厂。其确定性锁步方案交换输入，让各端按同一规则推进模拟；只要某端计算出现差异，就可能不同步，需要日志和状态对比定位原因。[20](#ref-20) 这说明“联网”可能改变整个状态验证方法，不能只理解为多加一个房间按钮。

<a id="visual-production"></a>

## 06｜美术与资源：从可编辑内容到游戏画面

美术阶段先确定目标镜头、轮廓、色彩与信息层次，再制作和导出。检查资源时同时看源工程与游戏里的实际显示；导出文件通常只保留源工程中的一部分能力。

### 二维图像与视觉组织

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 概念美术 | Concept Art | コンセプトアート | 探索造型、氛围和方向的图像；不一定直接作为运行资源 |
| 视觉参考板 | Mood Board / Reference Board | ムードボード／リファレンスボード | 把相关形状、材料、色彩与资料放在一起比较，保留来源与用途 |
| 资源／源工程 | Asset / Source Project | アセット／制作元データ | 游戏使用的内容／保留图层、节点等编辑能力的文件 |
| 位图／矢量图 | Raster / Vector | ラスター／ベクター | 以像素保存画面／以曲线和形状保存图形；缩放与编辑方式不同 |
| 像素画 | Pixel Art | ドット絵／ピクセルアート | 在有限像素尺度上控制形状、色彩和边缘；低分辨率显示本身不等于经过像素设计 |
| 调色板／抖色 | Palette / Dithering | パレット／ディザリング | 使用的颜色集合／用颜色排列模拟过渡；影响清晰度与纹理感 |
| 精灵／精灵表 | Sprite / Sprite Sheet | スプライト／スプライトシート | 游戏中的二维图像表现／把多个帧或图像排列在同一张图里 |
| 纹理图集 | Texture Atlas | テクスチャアトラス | 将多个纹理区域合并并记录位置；减少切换的效果需结合实际渲染方式判断 |
| 图块／图块地图 | Tile / Tilemap | タイル／タイルマップ | 可重复使用的小块图像／用排列与数据组成的地图 |
| 基点 | Pivot / Origin | ピボット／原点 | 对齐、旋转或放置资源时的参考位置；各帧不一致会造成抖动 |
| 透明通道 | Alpha Channel | アルファチャンネル | 表示透明程度；透明边缘需要与过滤、背景一起检查 |
| 最近邻／线性过滤 | Nearest / Linear Filtering | 最近傍／線形フィルタリング | 纹理采样方法；前者保留硬像素边界，后者混合邻近颜色 |
| 九宫格缩放 | Nine-slice | 9スライス | 分开处理面板四角、边缘与中心，改变大小时保留边框形状 |
| 视差 | Parallax | パララックス／視差 | 不同深度层以不同速度移动，制造空间感；常见于二维背景 |

### 三维形体、表面与渲染

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 网格／多边形 | Mesh / Polygon | メッシュ／ポリゴン | 由顶点、边和面构成的几何形状；多边形数量只是资源成本的一部分 |
| 拓扑／重拓扑 | Topology / Retopology | トポロジー／リトポロジー | 几何连接结构／重新组织连接；影响变形、编辑与运行效率 |
| 雕刻 | Sculpting | スカルプト | 以推拉、刻画等方式塑造形体；精细结果常需后续整理 |
| UV 展开 | UV Unwrapping | UV展開 | 建立模型表面与二维纹理位置的对应；需要处理接缝、拉伸和重叠 |
| 纹理／材质／着色器 | Texture / Material / Shader | テクスチャ／マテリアル／シェーダー | 图像或采样数据／表面显示参数组合／计算显示结果的程序；三者相互配合 |
| 基础色／粗糙度／金属度 | Base Color / Roughness / Metallic | ベースカラー／粗さ／メタリック | 常见表面参数；分别参与底色、反射散布和金属表面的描述 |
| 法线／法线贴图 | Normal / Normal Map | 法線／法線マップ | 表面朝向／用纹理改变受光计算中的方向；通常不会改变物体外轮廓 |
| 基于物理的渲染 | PBR — Physically Based Rendering | 物理ベースレンダリング | 用较一致的表面与光照模型组织材质；仍需要正确资源、参数和艺术选择 |
| 烘焙 | Baking | ベイク／ベイキング | 把部分计算提前写进资源，如法线、光照或动画数据；与现场实时计算分工 |
| 环境遮蔽 | Ambient Occlusion — AO | アンビエントオクルージョン | 表现局部遮挡带来的明暗线索；不能替代所有照明和接触阴影 |
| 细节层级 | Level of Detail — LOD | 詳細度レベル／LOD | 按距离等条件使用不同精度资源，降低运行开销并控制切换观感 |
| 剔除 | Culling | カリング | 跳过当前不需要处理或绘制的对象；如视野之外或被遮挡的内容 |
| 实时／预渲染 | Real-time / Pre-rendered | リアルタイム／プリレンダリング | 运行时计算画面／提前输出图像或视频；自由视角与交互能力不同 |
| 后期处理 | Post-processing | ポストプロセス | 对画面进一步处理，如调色、泛光和景深；需要检查文字与交互物可读性 |
| 色彩空间 | Color Space | 色空間 | 对颜色数值的解释方式；颜色贴图与法线等数据纹理通常采用不同设置 |
| 抗锯齿 | Anti-aliasing — AA | アンチエイリアシング | 减轻采样造成的阶梯边缘与闪烁；不同方法在清晰度、拖影和性能间取舍 |
| 光照贴图／反射探针 | Lightmap / Reflection Probe | ライトマップ／リフレクションプローブ | 保存预计算光照／采样环境反射信息；场景或物体变化后可能需要更新 |
| 正交／透视投影 | Orthographic / Perspective Projection | 平行投影／透視投影 | 远近不改变投影比例／远处物体显得更小；影响空间阅读和资源制作 |
| 分辨率／纹素密度 | Resolution / Texel Density | 解像度／テクセル密度 | 图像像素数量／模型单位长度对应多少纹理像素；影响细节与一致性 |

### 同一个问题：怎样持续制作大量二维动作

| 游戏、画面与动作需求 | 采用的路径与理由 | 结果及修改时的差异 |
| --- | --- | --- |
| [《Hollow Knight》](https://www.hollowknight.com/)：虫形角色在洞穴中跑跳、挥武器和战斗 | 用 Photoshop 手绘动画，再把 PNG 接入 Unity；团队利用现成功能，把更多精力放在擅长的美术上 | 轮廓和姿态由二维绘制直接控制；改姿态要回到画稿和动画帧。[6](#ref-6) |
| [《Cuphead》](https://cupheadgame.com/)：杯头角色与夸张变形的敌人进行横向射击战斗 | 纸上绘制动画，再数字上色。团队明确希望通过传统方法接近 1930 年代动画的表现 | 动作的形变与笔触成为风格的一部分，新增或大改动作会影响连续绘制工序。[7](#ref-7) |
| [《Dead Cells》](https://dead-cells.com/)：像素外观角色频繁更换武器、近身攻击和闪避 | 在三维中制作模型和动作，再转成小尺寸帧。美术师需要在有限人力下快速修改招式 | 调整攻击速度可移动关键帧后重新输出，装备和模型也可复用；小尺寸像素结果仍需检查。[8](#ref-8) |

三者最终都能用二维帧显示，差别在**姿态从哪里来、什么最值得保留、修改要返回哪个环节**。具体软件职责见 [002 的二维案例](posts-2026-umwelt-game-development-handbook-002.html#art-cases)。

<a id="levels-animation"></a>

## 07｜关卡、动画与表现：让空间和动作能够游玩

环境美术安排可见内容，关卡设计安排路线、目标、障碍与节奏；动画展示动作，规则决定动作何时生效。两组工作都需要在游戏中相互检查。

### 空间与引导

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 关卡设计 | Level Design | レベルデザイン | 安排空间、遭遇、引导和挑战顺序；关卡不一定是一张独立地图 |
| 场景布置 | Scene Assembly / Set Dressing | シーン構築／セットドレッシング | 把环境与装饰资源组成画面；装饰可能影响视线、遮挡和碰撞 |
| 粗搭 | Blockout | ブロックアウト | 用简单体块搭建空间，先验证尺度与通行，再细化美术 |
| 关键路线／支路 | Critical Path / Optional Path | 必須ルート／寄り道 | 完成主要目标所需路线／可选择的探索路线；此处 Critical Path 指游玩路径 |
| 地标／视线 | Landmark / Sightline | ランドマーク／視線 | 易识别的参照物／玩家从某处能看到的范围；共同支持方向判断 |
| 引导／新手教学 | Guidance / Onboarding | 誘導／導入・チュートリアル | 帮助玩家发现目标、学习操作和理解反馈；可通过布局、情境或提示完成 |
| 进度门槛 | Gating | ゲーティング／進行制限 | 通过能力、钥匙、知识或任务条件限制推进；门槛应有可理解的解除方式 |
| 检查点 | Checkpoint | チェックポイント | 失败后恢复的位置或状态；间距决定重复劳动和失败成本 |
| 节奏 | Pacing | ペーシング／緩急 | 挑战、休息、探索、叙事在时间上的安排 |
| 遭遇设计 | Encounter Design | エンカウンターデザイン | 安排某段战斗或互动中的对象、空间、行为和时序 |
| 导航网格／寻路 | NavMesh / Pathfinding | ナビメッシュ／経路探索 | 可通行区域表示／查找路线的方法；角色为什么移动还由行为系统决定 |
| 行为树 | Behavior Tree | ビヘイビアツリー／行動木 | 用条件与动作组织角色决策；与实际移动、动画和感知相连接 |

### 动画与动作规则

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 逐帧动画 | Frame-by-frame Animation | フレーム・バイ・フレーム／コマアニメーション | 逐张安排画面；可以来自手绘，也可以来自三维渲染 |
| 关键帧／插值 | Keyframe / Interpolation | キーフレーム／補間 | 指定重要时刻的值或姿态／计算中间变化；节奏取决于两者配合 |
| 骨架／绑定 | Skeleton / Rigging | スケルトン／リギング | 形体的骨骼结构／建立控制关系；控制器不一定直接进入成品 |
| 蒙皮／权重 | Skinning / Weight | スキニング／ウェイト | 让网格跟随骨骼／各部分受骨骼影响的比例 |
| 正向／反向运动学 | Forward Kinematics — FK / Inverse Kinematics — IK | フォワード／インバースキネマティクス | 逐级设置关节／根据末端目标求关节姿态；如按手部目标调整手臂 |
| 动画片段／混合 | Clip / Blending | アニメーションクリップ／ブレンド | 一段动作数据／在不同动作之间过渡或组合 |
| 根运动 | Root Motion | ルートモーション | 由动画中的根部位移驱动角色移动；需与碰撞和控制规则配合 |
| 动画事件 | Animation Event | アニメーションイベント | 在指定动作时刻触发声音、特效或规则；动作速度改变后需要重新核对 |
| 碰撞体 | Collider | コライダー／衝突形状 | 用于碰撞检测的形状；可以比可见模型简单 |
| 攻击判定／受击判定 | Hitbox / Hurtbox | 攻撃判定／食らい判定 | 攻击生效的区域／可以被命中的区域；术语在项目中可能另有约定 |
| 前摇／生效／后摇 | Startup / Active / Recovery | 発生前／持続／硬直 | 动作准备、判定有效和恢复阶段；与画面总时长分别设计 |
| 顿帧／屏幕震动 | Hit Stop / Screen Shake | ヒットストップ／画面揺れ | 短暂停顿／移动镜头来强化反馈；力度与可读性、舒适度共同考虑 |
| 粒子／视觉特效 | Particle / VFX | パーティクル／視覚エフェクト | 控制大量小元素／更广义的视觉效果；烟、火花与魔法可由多种技术组合 |

### 同一个问题：怎样让玩家知道接下来去哪

- [《Celeste》](https://www.celestegame.com/)把主要动作挑战放在相对紧凑的房间。玩家通常能看到平台、危险与出口，因此可以把注意力放在“这几步怎么连起来”。局部空间适合反复练习，但镜头与障碍必须清楚展示动作条件。
- [《Hollow Knight》](https://www.hollowknight.com/)让玩家在相互连接的洞穴房间中探索。岔路、地图和暂时无法通过的障碍共同形成长线判断：现在继续走，还是获得能力后返回。迷路与重新认识旧地点成为体验的一部分。
- [《A Short Hike》](https://ashorthike.com/)给出登顶方向，同时允许攀爬、绕路和滑翔。山体与可见地形让目标持续存在，沿途活动又支持自由偏离路线。这里需要让地形本身可读，而不是把每段路都变成单一答案。
- [《Outer Wilds》](https://www.mobiusdigitalgames.com/outer-wilds.html)用遗迹信息、声音信号和环境变化引出新目标。某个地点何时可进入也可能是问题的一部分，因此玩家会根据发现改变出发时机。[19](#ref-19)

这是对公开玩法的比较：**局部出口、互联地图、可见地形、信息线索**分别承担主要引导。关卡工具应当支持这些需要，详见 [002 的地图与关卡工具](posts-2026-umwelt-game-development-handbook-002.html#tools-07)。

## 08｜叙事、界面与声音：让内容跟随状态，并能被理解

文本、界面与声音都需要知道当前发生了什么。叙事读取关系和事件，界面显示可操作的状态，声音响应环境和行动；三者与规则一起制作，才能避免“内容存在，游戏却没有正确调用”。

### 叙事与文本

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 叙事设计 | Narrative Design | ナラティブデザイン | 安排故事、世界、玩家行为与系统之间的关系 |
| 世界观／背景设定 | Worldbuilding / Lore | 世界観構築／設定 | 世界的规则、历史和文化；其中哪些进入游戏，需要继续选择 |
| 故事节拍 | Story Beat | ストーリービート | 一次有意义的情节或情绪变化；不必等同于一个场景 |
| 分支／汇合 | Branch / Reconvergence | 分岐／合流 | 选择后进入不同内容／重新回到共享内容；汇合时仍可保留状态差异 |
| 条件／标记 | Condition / Flag | 条件／フラグ | 判断是否呈现某段内容／记录某事是否发生；是对白和任务连接的基础 |
| 对白树 | Dialogue Tree | 会話ツリー | 展示对白节点和选项关系；复杂项目也可能用脚本、表格或其他结构 |
| 环境叙事 | Environmental Storytelling | 環境ストーリーテリング | 通过物件位置、痕迹和空间关系提供故事信息 |
| 脚本事件／过场 | Scripted Event / Cutscene | スクリプトイベント／カットシーン | 按预设条件执行的事件／以镜头和表演呈现的段落；需要处理跳过、中断和状态 |
| 任务系统 | Quest System | クエストシステム | 管理目标、前提、进行状态与奖励；任务文字和实际条件必须一致 |
| 本地化／国际化 | Localization — L10n / Internationalization — I18n | ローカライズ／国際化 | 为特定语言地区调整内容／让系统能容纳这些变化；包含布局、字体和格式 |

### 同一个问题：玩家行动不一样，故事怎样跟着变化

| 游戏与玩家行为 | 具体组织方式 | 做法的作用与成本 |
| --- | --- | --- |
| [《80 Days》](https://www.inklestudios.com/80days/)：规划环球旅行路线，同时处理钱、时间和旅途事件 | 城市、路线与选择连接成旅程；ink 支持条件片段、分支和汇合 | 不同选择可以留下影响，又复用后续文本。重点是状态与文字之间的对应，并检查多种路线。[3](#ref-3) |
| [《Hades》](https://www.supergiantgames.com/games/hades/)：多次战斗后返回同一据点 | 把反复出现的地点与人物变化结合；战斗失败后仍可能接到新的关系和故事内容 | 重复返回仍能带来新信息。成本转向大量状态下的对白安排和连续性检查。[2](#ref-2) |
| [《Return of the Obra Dinn》](https://obradinn.com/)：以不同顺序调查船员的死亡现场 | 过去发生的事是既定的，玩家改变的是调查顺序与理解 | 历史无需随每次选择重写，但线索必须支持不同发现顺序；“非线性”也可以来自信息获得顺序 |

三者分别让变化落在**旅程与选择、反复游玩中的人物状态、玩家理解**上。编剧要先知道哪一层可以变化，再决定文本和分支体量。若十次二选一始终不汇合，就会形成 1,024 条路径；汇合、条件片段和共享场景可以控制扩张。

### 界面、输入与可读性

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 用户界面／使用体验 | User Interface — UI / User Experience — UX | ユーザーインターフェース／ユーザー体験 | 控件与信息呈现／理解、操作、反馈的整体体验；界面漂亮并不自动说明操作清楚 |
| 游戏内信息层 | HUD — Heads-up Display | HUD／ゲーム内情報表示 | 游玩中持续或即时显示的生命、地图、弹药等信息 |
| 线框图／交互原型 | Wireframe / Interactive Prototype | ワイヤーフレーム／インタラクション試作 | 先安排信息结构／再尝试操作和页面流转；仍需连接实际状态 |
| 响应式布局 | Responsive Layout | レスポンシブレイアウト | 随屏幕和内容改变排列、大小与留白；要检查长文本和不同输入 |
| 焦点／导航 | Focus / Navigation | フォーカス／ナビゲーション | 当前接受输入的控件／控件之间移动方式；键盘与手柄尤其依赖此关系 |
| 按键重映射 | Input Remapping | キーコンフィグ／入力割り当て変更 | 允许把动作重新分配给按键或控制器输入 |
| 无障碍 | Accessibility | アクセシビリティ | 减少感知、操作和理解障碍，如字幕、字号、替代反馈和输入调整 |
| 世界内界面 | Diegetic UI | ダイジェティックUI／世界内UI | 信息以世界中的物体或装置呈现；仍要确保玩家能读到和操作 |

### 声音与交互音频

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 背景音乐／音效／配音 | Background Music — BGM / Sound Effects — SFX / Voice-over — VO | BGM／SE・効果音／ボイス | 音乐、行动或环境声音、角色语音；音量和优先级可分别管理 |
| 环境声／拟音 | Ambience / Foley | 環境音／フォーリー | 空间与环境的声音层／为动作制作或录制的声音，如衣料与脚步 |
| 数字音频工作站 | Digital Audio Workstation — DAW | デジタルオーディオワークステーション | 录音、编辑、编曲和混音的制作环境；输出素材后还需游戏接入 |
| 声音事件／参数 | Audio Event / Parameter | オーディオイベント／パラメータ | 可触发的声音行为／影响播放的数值或状态；如速度改变引擎声 |
| 自适应音乐 | Adaptive Music | アダプティブミュージック | 音乐随状态变化；可改变层、段落、强度和衔接位置 |
| 分轨／音乐层 | Stem / Layer | ステム／レイヤー | 可独立处理的声部或子混音／运行中可分别控制的层；用法随工程而异 |
| 循环点／交叉淡化 | Loop Point / Crossfade | ループポイント／クロスフェード | 重复播放的边界／两段声音交叠渐变；用于减少突变和接缝 |
| 总线／混音／空间音频 | Bus / Mixing / Spatial Audio | バス／ミキシング／空間オーディオ | 成组控制声音／安排相对音量和处理／根据位置等组织听觉关系 |

[《Untitled Goose Game》](https://goose.game/)让玩家扮演鹅，在村庄里偷东西、引人追赶。配乐采用预先录好的钢琴材料，由系统随情境组织，给即兴行动配出接近默片喜剧的节奏。作曲者说明了这种动态音乐怎样借鉴电影伴奏。[18](#ref-18) 因此，“音乐写完”之后仍有事件、状态与衔接的制作；更多声音方案比较见 [002](posts-2026-umwelt-game-development-handbook-002.html#audio-cases)。

## 09｜正式制作与协作：把样板扩展成完整作品

正式制作按已经验证的方法增加功能与内容。每轮完成制作、接入和检查，留下可玩的版本；源工程、导出资源和成品分别保存，便于继续修改与追查。

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 正式制作 | Production | 本制作／プロダクション | 将经过验证的设计与流程扩展成完整项目 |
| 迭代 | Iteration | イテレーション／反復改善 | 制作、检查、得到信息后再修改；每轮应有明确问题和范围 |
| 功能／内容 | Feature / Content | 機能／コンテンツ | 可复用的能力／利用能力制作的具体材料；新内容也可能引入新功能 |
| 接入／整合 | Integration | 組み込み／統合 | 让程序、资源与其他系统一起运行；导出一个文件还没有完成接入 |
| 版本管理 | Version Control | バージョン管理 | 记录文件变化、比较和恢复版本，支持多人协作 |
| 提交／分支／合并 | Commit / Branch / Merge | コミット／ブランチ／マージ | 保存一组变化／独立推进一条修改线／把修改接回共同版本 |
| 审查／合并请求 | Review / Pull Request | レビュー／プルリクエスト | 提出并检查修改；审查结果应对应实际文件和行为 |
| 冲突／文件锁 | Conflict / File Lock | コンフリクト／ファイルロック | 修改无法自动合并／限制同时修改；模型等二进制工程常需明确交接 |
| 备份 | Backup | バックアップ | 独立保存可恢复副本；要覆盖源工程、大资源、依赖和必要配置 |
| 单一可信来源 | Single Source of Truth | 一元的な正本管理 | 明确哪份数据或文件是当前依据，减少多个副本各自更新 |
| 重构 | Refactoring | リファクタリング | 保持约定行为的前提下调整内部结构，使修改与理解更容易 |
| 技术债务 | Technical Debt | 技術的負債 | 增加后续修改负担的设计或实现问题；应结合影响和修复成本处理 |
| 功能冻结／内容冻结 | Feature Freeze / Content Freeze | 機能凍結／コンテンツ凍結 | 暂停新增功能／内容，把精力转向稳定和发布；范围由团队明确 |
| 变更请求 | Change Request | 変更要求 | 对已约定内容提出修改，重新评估依赖、成本与验收 |

### 同一个问题：“再加一个”到底增加多少工作

| 例子 | 可能复用的部分 | 需要继续制作或检查的部分 |
| --- | --- | --- |
| [《星露谷物语》](https://www.stardewvalley.net/)式种植系统新增一种普通作物 | 种植、浇水、成熟与收获规则 | 图像、价格、季节、物品关系；若会追着玩家跑，就已经引入新行为 |
| [《Hollow Knight》](https://www.hollowknight.com/)式探索新增一间房 | 移动、战斗、门和保存系统 | 地形、美术、敌人组合；还要检查已有能力能否绕过障碍 |
| [《Papers, Please》](https://papersplea.se/)式检查新增一种证件 | 展示、比对、裁决的基本能力 | 字段、规则、文字和例外；新字段还可能与旧证件产生交叉条件 |
| [《80 Days》](https://www.inklestudios.com/80days/)式旅行新增一座城市 | 路线与条件叙事框架 | 城市事件、路线、资源变化以及抵达时的多种状态 |

这是基于玩法的制作估算示例，不是这些项目的内部任务记录。判断新增工作时，先看它是否仍在已有规则内，再数资源和组合。

<a id="cost"></a>

### 预算与进度

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 工时估算 | Effort Estimation | 工数見積もり | 估计完成任务需要多少劳动时间；用实际样板校准 |
| 人日／日历工期 | Person-day / Elapsed Time | 人日／所要期間 | 工作量／从开始到结束经过的时间；等待和依赖会让两者不同 |
| 预算／消耗速度 | Budget / Burn Rate | 予算／バーンレート | 可用资金／单位时间消耗；与剩余工作和可持续时间一起判断 |
| 制作吞吐量 | Throughput | スループット | 一段时间实际完成并接入多少内容；只数未检查资源会高估进度 |
| 总拥有成本 | Total Cost of Ownership — TCO | 総保有コスト | 获取、学习、接入、运行和维护的总体成本；软件价格只是其中一项 |

**剩余工作 ≈ 各类内容数量 × 对应实测工时 ＋ 共用系统 ＋ 整合测试 ＋ 返工与发布预留。** 复杂角色、普通道具和远景分开估算；增加语言、平台或永久分支，也要增加对应验证工作。后续测试根据这些规格判断成品是否达到约定。

<a id="phase-6"></a>

## 10｜测试与打磨：区分规则正确、玩家理解与运行稳定

测试贯穿制作。临近发布时，需要从完整成品重新走主要流程，同时覆盖新存档、旧存档、失败、取消、重试、不同语言与目标设备。

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 质量保证 | Quality Assurance — QA | 品質保証／QA | 围绕质量建立的过程与检查；测试是其中一部分 |
| 调试／测试 | Debugging / Testing | デバッグ／テスト | 寻找并修复原因／检查结果；行业口语中“デバッグ”也可能泛指测试工作 |
| 试玩 | Playtest | プレイテスト | 观察实际玩家的理解、行为和体验；与自动化检查互补 |
| 单元／集成测试 | Unit / Integration Test | 単体／結合テスト | 检查较小规则单元／多个部分一起工作的情况 |
| 端到端测试 | End-to-end Test — E2E | エンドツーエンドテスト | 从实际入口走一段完整流程，核对各层连接 |
| 冒烟测试 | Smoke Test | スモークテスト | 快速确认启动、主要路径等关键能力，判断是否值得继续详细检查 |
| 回归测试 | Regression Test | リグレッションテスト／回帰テスト | 修改后检查原有行为是否被破坏 |
| 功能／体验测试 | Functional / Usability Test | 機能／ユーザビリティテスト | 是否按约定工作／人能否理解和顺利操作；两者问题来源可能不同 |
| 兼容／本地化测试 | Compatibility / Localization QA | 互換性／ローカライズQA | 不同设备和环境／具体语言的文字、布局、语境和流程 |
| 复现步骤／最小复现 | Reproduction Steps / Minimal Repro | 再現手順／最小再現例 | 如何再次触发问题／去掉无关内容后仍出现问题的最小条件 |
| 缺陷／严重度／优先级 | Bug / Severity / Priority | 不具合／重大度／優先度 | 不符合约定的问题／影响有多大／先处理哪一个；三者分别记录 |
| 崩溃／卡死／软锁 | Crash / Hang / Softlock | クラッシュ／フリーズ／進行不能 | 程序退出／不再响应／仍运行但无法继续必要进程 |
| 边界情况 | Edge Case | 境界ケース／例外的な条件 | 极端或少见条件，如空存档、最长文本、快速连点和中途断开 |
| 自动化测试 | Automated Test | 自動テスト | 由程序重复执行检查；通过只说明已覆盖的条件成立 |
| 遥测／分析 | Telemetry / Analytics | テレメトリ／分析 | 收集与解释运行或行为数据；采集内容、权限和用途应明确 |
| 日志／断点 | Log / Breakpoint | ログ／ブレークポイント | 保存执行信息／暂停到指定位置以检查状态 |
| 性能分析 | Profiling | プロファイリング | 测量时间、内存和图形等开销，定位瓶颈 |
| 帧率／帧时间 | Frames per Second — FPS / Frame Time | フレームレート／フレーム時間 | 每秒帧数／单帧耗时；平均帧率正常也可能有明显尖峰卡顿 |
| CPU／GPU 瓶颈 | CPU-bound / GPU-bound | CPU／GPUボトルネック | 处理器计算／图形计算成为主要限制；应依据测量选择优化方向 |
| 绘制调用／过度绘制 | Draw Call / Overdraw | ドローコール／オーバードロー | 提交绘制工作／同一像素被重复处理；成本随具体渲染方式变化 |
| 内存泄漏／回收 | Memory Leak / Garbage Collection | メモリリーク／ガベージコレクション | 不再需要的内存持续留存／自动回收部分不再使用对象；回收也可能产生耗时 |
| 长时间测试／压力测试 | Soak / Stress Test | 長時間／ストレステスト | 检查持续运行的累积问题／极端负载下的行为 |
| 打磨 | Polish | ポリッシュ／仕上げ | 改进节奏、反馈、过渡与一致性；建立在主要规则和内容已经成立的基础上 |

### 同一个问题：失败太挫折，究竟改哪里

| 游戏与失败情境 | 各自怎么处理 | 为什么适合；最后有什么不同 |
| --- | --- | --- |
| [《Celeste》](https://www.celestegame.com/)：玩家知道要跳到哪里，却可能因细小时间误差失败 | 短距离重试配合输入缓冲、离边宽限和边角修正 | 减少重复赶路与“明明按了却没跳”的挫折，把注意力留在动作学习上；主要挑战仍在操作。[10](#ref-10) |
| [《Baba Is You》](https://www.hempuli.com/baba/)：玩家试了一种文字排列，发现结果不对 | 允许撤销操作，再尝试另一种排列 | 推理需要试验，撤销减少重摆局面的成本；解题困难仍在理解规则，没有直接给答案 |
| [《Hades》](https://www.supergiantgames.com/games/hades/)：玩家还想看故事，但战斗伤害压力过高 | 可选择 God Mode，以减伤并随死亡提高耐受 | 调整的是承受压力，让玩家更容易继续体验；与修正按键时机、撤销一步操作解决的是不同问题。[2](#ref-2) |

“降低挫折”可能意味着**减少重复劳动、容纳操作误差、允许试验、降低数值压力**。先观察玩家在哪里受阻，才能判断该改输入、关卡、信息还是参数。

<a id="acceptance"></a>

### 验收怎样连接到发布

一份问题记录至少包含**版本、环境、起始状态、步骤、预期、实际和证据**。修复后先复测原问题，再检查可能受影响的流程。性能比较固定镜头、输入、设备和画质：60 帧每秒平均约为每帧 16.7 毫秒，但单帧波动还要单独观察。

发布判断应能说明：**哪个候选版本，在什么条件下，通过哪些检查，还有哪些未覆盖条件。** 例如网页音频受首次用户操作影响，模拟手机尺寸也不能完全替代真机检查。[9](#ref-9), [12](#ref-12) 这些结果随后决定哪个构建可以发布。

<a id="phase-7"></a>

## 11｜发布与发行：区分文件完成、平台接入和玩家取得

构建生成成品，部署把成品放进运行环境，发布让玩家取得约定版本。产品页、宣传材料、平台接入和审核也需要时间，通常在正式制作期间就开始准备。

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 构建／打包 | Build / Packaging | ビルド／パッケージ化 | 生成目标程序与资源／组织成可分发形式；不同平台有不同产物 |
| 构建产物 | Artifact | ビルド成果物／アーティファクト | 某次构建生成的文件；发布和测试应能追溯到同一份产物 |
| 持续集成／交付／部署 | Continuous Integration — CI / Continuous Delivery / Continuous Deployment | 継続的インテグレーション／デリバリー／デプロイ | 自动检查与整合／保持可发布状态／自动部署；CD 需按项目语境区分 |
| 部署／发布／发行 | Deploy / Release / Publishing | デプロイ／リリース／パブリッシング | 放入目标环境／开放版本／产品经营与分发支持；职责有交叉但不相同 |
| Alpha 阶段／Beta 阶段 | Alpha / Beta | アルファ／ベータ | 团队使用的成熟度标签；具体公开范围、功能与品质标准必须另写 |
| 功能齐备／内容齐备 | Feature Complete / Content Complete | 機能実装完了／コンテンツ完成 | 约定功能已实现／内容已接入；之后仍要测试、打磨和修复 |
| 候选发布版本 | Release Candidate — RC | リリース候補版 | 准备发布并接受最后检查的具体版本；再修改就需要重新确认 |
| 母版／发行批准 | Gold Master / Going Gold | マスター／マスターアップ | 达到某种正式生产或发布条件的版本；更新型游戏仍可能继续修补 |
| 抢先体验 | Early Access | 早期アクセス | 以明确未完成状态公开提供游戏并继续开发；需要维护当前版本与后续计划 |
| 平台审核／认证 | Review / Certification | 審査／認証 | 平台对商店内容、功能和技术要求的检查；通过范围以平台说明为准 |
| 移植 | Porting | 移植 | 让作品适应另一个平台的运行、输入和分发条件；不只是重新编译 |
| 最低／推荐配置 | Minimum / Recommended Requirements | 最低／推奨動作環境 | 对运行条件的说明；应与实测内容、画质和体验目标对应 |
| 商店页／愿望单 | Store Page / Wishlist | ストアページ／ウィッシュリスト | 展示并分发作品／玩家表达关注；数量是信号，不能直接等同销量 |
| 宣传片／媒体资料包 | Trailer / Press Kit | トレーラー／プレスキット | 展示体验的视频／供媒体使用的简介、图像和基本信息 |
| 发行商／自行发行 | Publisher / Self-publishing | パブリッシャー／自主販売 | 提供约定发行支持的合作方／自己承担相应工作；具体责任看合作安排 |
| 本体／追加内容 | Base Game / Downloadable Content — DLC | 本編／ダウンロードコンテンツ | 基础产品／追加内容；与补丁、免费更新分别安排 |
| 买断／免费游玩 | Premium / Free-to-play — F2P | 買い切り／基本プレイ無料 | 先购买本体／可免费开始；后续收费和服务范围仍需分别说明 |
| 许可证／署名 | License / Attribution | ライセンス／クレジット表記 | 使用与分发条件／按要求标明作者和来源；软件、字体、声音各自核对 |
| 年龄分级 | Age Rating | 年齢レーティング | 对内容与适用年龄等作出的分级；平台和地区要求分别确认 |
| 内容分发网络 | CDN — Content Delivery Network | コンテンツ配信ネットワーク | 从不同节点分发文件以改善获取；更新时还需处理缓存与版本对应 |

### 同一个问题：已经能玩，为什么还会在发布时出问题

| 游戏与变更 | 发生了什么、怎样处理 | 对应的发布知识 |
| --- | --- | --- |
| [《Baldur’s Gate 3》](https://baldursgate3.game/)：角色扮演游戏的 Hotfix 4 | 已测试候选后来为改版本号重新构建，出现编译问题；回退期间，部分新存档无法由旧版本读取。团队随后要求候选的任何更改重新接受完整检查 | 测过的构建与实际发布文件必须对应；回退也要考虑新存档。[14](#ref-14) |
| [《星露谷物语》](https://www.stardewvalley.net/)：PC 版 1.5.5 的运行技术更新 | 从 XNA 迁到 MonoGame，同时修复兼容与本地化等问题 | 玩家看到的内容可能变化不大，运行环境却变了；技术迁移需要重新验证支持条件。[15](#ref-15) |
| [《Hades》](https://www.supergiantgames.com/games/hades/)：抢先体验到 1.0 | 在公开可玩的阶段持续增加战斗与故事，再进入正式版本 | 公开发布是持续交付方式，团队要同时承担反馈、兼容和未完成内容的制作。[2](#ref-2) |

Steam 将商店页和构建分别审核，因此介绍材料与程序要分别准备，再检查彼此是否一致。[11](#ref-11) 发布后从公开入口重新取得成品，确认文件、输入、声音和进度恢复；只检查本地项目无法证明分发成功。

<a id="phase-8"></a>

## 12｜维护、扩展与结束支持

维护先区分缺陷、理解困难、设备差异、偏好和新增需求。补丁处理已确认的问题；扩展内容重新经过范围、依赖、制作与测试。停止扩展时，仍应留下可以恢复和继续使用的项目。

| 中文 | English | 日本語 | 含义与关系 |
| --- | --- | --- | --- |
| 补丁／紧急修复 | Patch / Hotfix | パッチ／ホットフィックス | 修改已发布版本／针对迫切问题快速发布修复；快速仍需明确验证范围 |
| 数据迁移 | Data Migration | データ移行 | 把旧结构转成新结构，如存档字段变化；应保存旧数据并验证转换 |
| 向后兼容 | Backward Compatibility | 後方互換性 | 新版本能继续处理旧内容或数据；不自动意味着旧程序也能读新数据 |
| 回退 | Rollback | ロールバック／切り戻し | 恢复之前的程序或配置；已经改变的数据需要单独处理 |
| 在线运营 | Live Operations — LiveOps | ライブ運営／運用 | 持续维护在线内容、活动、服务和运行状态 |
| 监控／告警 | Monitoring / Alerting | 監視／アラート | 持续观察服务与异常／在指定条件下提醒处理 |
| 留存／流失 | Retention / Churn | リテンション／離脱 | 某群玩家继续返回／停止使用的情况；先明确时间窗口和统计口径 |
| 更新记录 | Changelog / Release Notes | 変更履歴／リリースノート | 说明版本变化和必要的兼容信息；服务玩家与维护者 |
| 复盘 | Postmortem / Retrospective | ポストモーテム／振り返り | 根据结果检查原先假设、取舍和流程；形成下次可用的判断 |
| 停止支持／服务终止 | End of Life — EOL / End of Service | サポート終了／サービス終了 | 停止维护／停止在线服务；要说明对获取、存档和游玩的影响 |
| 归档／保存 | Archiving / Preservation | アーカイブ／保存 | 保存源工程、可运行成品、依赖版本、资源来源与重建说明 |

本地存档还受运行环境影响。例如浏览器 `localStorage` 与站点来源关联，换域名、浏览器或清理站点数据可能让原进度不可见或消失。[13](#ref-13) 因而长期保存作品时，要同时考虑**制作工程、运行程序、玩家数据和在线依赖**。

<a id="terms"></a>

## 类型名称与易混缩写

类型标签描述不同维度，可以叠加。用它们交流后，仍要具体说明玩家行为；例如“角色扮演”并不能说明战斗是即时还是回合制。

| 中文／常见名称 | English | 日本語 | 描述的重点与边界 |
| --- | --- | --- | --- |
| 角色扮演／动作角色扮演 | Role-playing Game — RPG / Action RPG — ARPG | ロールプレイングゲーム／アクションRPG | 角色能力、成长与扮演／结合即时动作的 RPG；RPG 不等于必然有回合制战斗 |
| 第一／第三人称射击 | First-person Shooter — FPS / Third-person Shooter — TPS | 一人称／三人称視点シューティング | 射击玩法与相机位置；FPS 在性能语境中另指每秒帧数 |
| 平台跳跃 | Platformer | プラットフォームゲーム／ジャンプアクション | 以跳跃和空间移动为重要挑战，如[《Celeste》](https://www.celestegame.com/)；也可结合探索与战斗 |
| 冒险／指向点击冒险 | Adventure / Point-and-click Adventure | アドベンチャー／ポイント＆クリック | 探索、叙事和解谜等结构／通过指向场景、物品交互推进；“冒险”用法较宽 |
| 视觉小说／文字冒险 | Visual Novel / Text Adventure | ビジュアルノベル／テキストアドベンチャー | 以文字、图像和选择等推进／以文字描述与输入或选项组织行动；二者不完全重合 |
| 即时／回合制策略 | Real-time Strategy — RTS / Turn-based Strategy — TBS | リアルタイムストラテジー／ターン制ストラテジー | 多方同时推进／按回合推进；重点常在单位、资源与空间决策 |
| 多人在线战术竞技 | MOBA — Multiplayer Online Battle Arena | MOBA | 常见结构是队伍控制角色、围绕地图目标对抗；具体人数和规则由作品决定 |
| 类银河战士恶魔城 | Metroidvania | メトロイドヴァニア | 相连地图、探索与能力获得共同打开路线；回到旧区域也能产生新进展 |
| Roguelike／Roguelite | Roguelike / Roguelite | ローグライク／ローグライト | 常涉及多轮尝试、变化的局面与失败后的重置；两词边界有争议，要具体说明随机、重置与永久成长 |
| 沙盒／开放世界 | Sandbox / Open World | サンドボックス／オープンワールド | 强调自由组合行动／强调可自由探索的世界组织；开放地图不自动意味着规则自由 |
| 模拟／经营 | Simulation / Management | シミュレーション／経営・管理 | 模拟某种系统／围绕资源与组织作决策；日文“シミュレーション”还常出现在策略游戏分类中 |
| 实时／回合制 | Real-time / Turn-based | リアルタイム／ターン制 | 时间与行动怎样推进，能用于描述战斗、策略或其他系统；与美术的实时渲染分别理解 |

### 容易在不同语境中变义的名称

| 名称 | 应怎样区分 |
| --- | --- |
| 核心循环 Core Loop／游戏循环 Game Loop | 玩家反复进行的行为结构／程序反复更新的执行过程 |
| TDD | 技术设计文档 Technical Design Document；也可能是测试驱动开发 Test-driven Development（日：テスト駆動開発） |
| FPS | 每秒帧数 Frames per Second；也可能是第一人称射击 First-person Shooter（日：一人称視点シューティング） |
| AI | 游戏角色决策等 Artificial Intelligence；生成式 AI 是其中另一个语境；`.ai` 还可能是 Illustrator 文件 |
| QA／QC | Quality Assurance 关注质量过程，Quality Control 关注结果检查；岗位用法需看团队约定 |
| 关键路径 Critical Path | 计划中决定工期的依赖链；关卡中通向主要目标的必要路线 |
| 原型／切片／Demo | 验证假设／验证目标品质与生产方法／给特定受众体验；一个版本可以兼具用途 |
| 实时三维／三维预渲染 | 玩家运行时计算画面／制作时提前输出图像或帧；最终二维外观不能证明源工程也是二维 |
| 存档／版本管理／备份 | 保存玩家进度／记录开发修改／保留可恢复副本；三者都需要但职责不同 |
| Build／Deploy／Release | 生成产物／放入目标环境／开放给玩家；每一步都应检查实际结果 |

这条流程最终连接的是：**概念确定取舍，规则定义行为，原型验证体验，切片验证生产，正式制作扩展内容，测试提供发布依据，维护保证后续可用。** 查到单个术语后，可以回到它所在的阶段，确认前提、交付和下一步。
