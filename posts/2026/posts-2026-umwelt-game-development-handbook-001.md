# 游戏开发流程手册｜ChatGPT 写给五月七日的指导笔记 001

**撰写：ChatGPT · 初次整理：2026-10-13**

**001 制作流程** · [002 软件地图与查阅](posts-2026-umwelt-game-development-handbook-002.html)

游戏开发要把四件事接起来：**玩家得到什么体验，规则怎样产生这种体验，内容怎样持续制作，成品怎样交到玩家手里。** 想法、程序、美术、声音、测试和发行都围绕这条关系安排。

本篇按制作顺序阅读，帮助你理解全局、安排工作和判断交付。具体编程可以由开发者或 AI 完成；你仍需要看懂每个阶段留下什么成果，以及哪些结果值得继续投入。工具的用途、费用和文件交接另见 [002](posts-2026-umwelt-game-development-handbook-002.html)。

<a id="overview"></a>
## 全流程速查

| 阶段 | 核心工作 | 应留下的成果 | 继续投入的依据 |
| --- | --- | --- | --- |
| [1. 体验与范围](#phase-1) | 确定玩家行为、平台、体量和约束 | 一页概念、首版清单、主要风险 | 能说明首版做什么，并排出最不确定的事 |
| [2. 设计与计划](#phase-2) | 写清规则、状态、内容结构与分工 | 简版设计、资源规格、任务与依赖 | 参与者能据此制作和检查同一件东西 |
| [3. 原型验证](#phase-3) | 用小规模尝试检验关键假设 | 可玩的原型、观察与取舍 | 核心行为成立，关键技术有可行路径 |
| [4. 制作样板](#phase-4) | 做一段接近目标品质的完整体验 | 垂直切片、质量基准、实测工时 | 效果达标，而且能按可承受成本重复制作 |
| [5. 内容生产](#phase-5) | 制作、接入、测试，再持续扩展 | 不断可玩的版本、源文件和资源 | 新内容能稳定进入游戏，没有持续积压在交接处 |
| [6. 测试与打磨](#phase-6) | 验证规则、体验、兼容和性能 | 问题清单、检查结果、候选版本 | 阻断问题已解决，剩余问题在约定范围内 |
| [7. 发布](#phase-7) | 交付经过检查的实际成品 | 安装包或网站、发布材料、恢复方案 | 从公开入口取得的版本能按预期运行 |
| [8. 维护](#phase-8) | 处理反馈、兼容、补丁与结束支持 | 稳定版本、更新说明、可恢复的项目 | 后续投入有明确目的，旧内容仍可使用 |

小项目可以合并阶段。例如，一间房里的对话游戏可以在同一个可玩版本中验证规则、画面和制作方法。阶段是否分开取决于体量，**体验是否成立、能否持续制作、能否可靠交付**这三项判断都应保留。测试、预算、资料核查和宣传准备也会贯穿制作过程。

<a id="phase-1"></a>
## 1｜确定体验与首版范围

先用一段话写出：玩家扮演谁，在什么情境下，反复做什么，怎样知道行动有效，最后得到怎样的体验。“一个关于海上旅行的游戏”给出了题材；“玩家在渡轮上观察邻座、选择回应，并从对方的动作理解关系变化”进一步给出了可以制作的行为。

接着确定平台、输入方式、预计时长、视觉形式、人数与可用时间。手机竖屏和桌面键鼠会影响按钮、文字与构图；自由转动视角和固定镜头会影响模型与画面生产；本地单机和实时联机会影响状态、服务与测试。这些选择越晚改变，已经完成的内容越可能返工。

<a id="core-loop"></a>
### 核心循环：玩家反复做什么

核心循环把**行动、反馈和下一次决定**接起来。下表是根据作品公开玩法作出的结构分析，便于比较；开发过程的事实另引开发者资料。

| 游戏 | 反复出现的行为 | 玩家得到的反馈 | 设计时需要优先验证的关系 |
| --- | --- | --- | --- |
| [《星露谷物语》](https://www.stardewvalley.net/) | 安排一天 → 耕作、采集或交往 → 处理所得 → 规划下一天 | 作物、金钱、设施与人物关系变化 | 时间和资源是否让日常选择有意义 |
| [《Celeste》](https://www.celestegame.com/) | 观察地形 → 跳跃与冲刺 → 失败或抵达 → 再尝试 | 位置、动作结果和新的可达区域 | 玩家是否看得懂失败，并能修正下一次操作 |
| [《Papers, Please》](https://papersplea.se/) | 检查证件 → 找出矛盾 → 作出裁决 → 接待下一人 | 警告、收入与人物处境 | 信息量、时间压力和判断后果怎样共同起作用 |
| [《Return of the Obra Dinn》](https://obradinn.com/) | 查看现场 → 比对线索 → 推断身份与命运 → 查找更多证据 | 推断之间的相互支持与确认 | 线索能否支撑推理，误解后能否继续调查 |
| [《Outer Wilds》](https://www.mobiusdigitalgames.com/outer-wilds.html) | 出发探索 → 发现信息 → 形成新问题 → 再次探索 | 对地点、事件和世界规律的理解 | 新知识是否给玩家提供可行动的方向 |

这些循环的进展可以表现为数值、操作熟练度、关系或知识。观察游戏也可以让玩家通过识别细节继续行动；只要反馈能改变下一次选择，就有可检验的交互结构。

### 把范围写成可核对的数量

“做一个完整世界”很难估算。可以先写成“一处场景、两名可交流角色、一个完整事件、两种结局、中文、桌面浏览器”。再把内容分成首版必需、可延后和当前不做三栏。新增一项时，同时说明它增加多少制作与测试工作，或替换哪项原计划。

范围大小也要与体验密度一起看：

- **[《A Short Hike》](https://ashorthike.com/)**把徒步、攀爬、滑翔和相遇集中在一个小型探索空间。作者的复盘明确讨论了如何在四个月的初版期限内作出视觉、关卡与写作取舍。可以借鉴的是“用有限空间支持相互关联的活动”，四个月属于该项目的具体条件。[1](#ref-1)
- **[《Papers, Please》](https://papersplea.se/)**把大量变化放在证件、规则和来访者身上。固定工作地点仍然可以容纳丰富决定，但文字、组合规则和例外情况会增加内容与测试量。
- **[《Hades》](https://www.supergiantgames.com/games/hades/)**在反复挑战中展开战斗组合与人物事件，并采用抢先体验逐步迭代。Supergiant 的说明表明，连续扩展的叙事与公开开发方式在计划中彼此配合。[2](#ref-2)

因此，估算体量时同时数场景、动作、文本、状态和组合。只有一个房间的作品，也可能因为大量分支和角色反应而成为大项目。

**阶段成果：** 一页概念、首版数量、平台与输入、可用资源，以及按影响排序的风险。优先验证一旦失败就会推翻方案的部分。

<a id="phase-2"></a>
## 2｜把想法转成规则、资源与计划

设计文档（GDD）需要让参与者知道如何制作。小项目可以只用几页：体验目标、操作与状态、内容清单、资源规格、验收条件。没有决定的部分明确标为待验证，确定后再更新。

<a id="rules"></a>
### 规则与状态

一项规则至少写清**触发条件、前提、变化、反馈、结束或中断方式**。例如“点击杯子”还不足以实现：杯子是否可用、当前是否在对白中、点击后播放哪段动作、何时更新对白、连续点击怎样处理，都需要约定。

状态是游戏当前记住的情况，例如“已经看过船票”“对方是否回答”“当前地点”“音乐是否关闭”。界面和剧情读取这些状态，再决定显示什么。存档保存需要延续的部分；鼠标位置等临时信息通常无需长期保留。

| 作品 | 内容和规则怎样配合 | 适合比较的设计问题 |
| --- | --- | --- |
| [《Baba Is You》](https://www.hempuli.com/baba/) | 玩家移动文字，改变关卡规则 | 可修改的规则如何立即改变可行动作 |
| [《Papers, Please》](https://papersplea.se/) | 证件信息与当日检查规则共同决定判断 | 普通规则、例外和冲突怎样清楚呈现 |
| [《80 Days》](https://www.inklestudios.com/80days/) | 路线、资源和故事选择共同推进旅程 | 文本怎样读取过去的选择，并影响之后的事件 |
| [《Hades》](https://www.supergiantgames.com/games/hades/) | 反复出发与返回连接战斗和人物事件 | 重复游玩时，哪些变化保留，哪些重新开始 |

前两例让规则直接进入操作，后两例让叙事依赖状态。借鉴时，可以先画出几种关键状态及其连接，再补写对白与资源。ink 的开发者演讲展示了《80 Days》背后的叙事脚本思路；它可以帮助理解文本内容和运行系统怎样分工。[3](#ref-3)

分支也不必始终分裂。两种回应可以在下一场景汇合，同时保存一个关系差异，让后文产生不同反应。假设每次二选一都永久分开，连续十次就会形成 1,024 条路径；这是不汇合条件下的组合示例。实际设计可以通过汇合、条件片段和共享场景控制制作量。

### 资料怎样变成游戏内容

使用历史、自然科学或真实地点时，先保留原始出处，再写工作性解释，最后说明游戏采用的简化。比如资料中的动物行为需要附条件和证据；“为了让变化更容易观察而缩短等待时间”属于游戏参数。两者分开记录，后续修订事实时才能判断哪些文字、模型和规则受到影响。

以你的 UMWELT 为例，可以把“新增一段生境观察”写成设计练习：资料决定需要呈现哪些可观察差异，规则决定玩家怎样发现它们，美术与文本决定差异怎样被看见。这是任务组织示例，具体功能以项目当前实现为准。

### 资源、分工与依赖

| 工作 | 交付内容 | 交接时需要说清 |
| --- | --- | --- |
| 游戏与叙事设计 | 操作、状态、场景、对白和结果 | 条件、例外、分支、稳定标识与验收 |
| 程序 | 输入、规则、存档、界面和系统连接 | 运行入口、依赖、错误处理、版本与检查范围 |
| 美术与动画 | 可编辑源工程、导出资源、动作 | 尺寸、比例、相机、帧率、命名、导出方式 |
| 音频 | 音源、分轨、循环片段、声音事件 | 触发、衔接、音量、停止条件与运行文件 |
| 测试与制作协调 | 任务排序、问题、验证与决定 | 当前采用哪个版本，谁制作、谁检查、谁决定 |

一人可以承担多个职责，但交付关系仍然存在。例如，动画需要明确攻击生效时刻，碰撞与声音才能接上；对白需要稳定编号，本地化和存档才能持续引用。依赖尚未确定时，先做可替换的小样，减少连带返工。

**阶段成果：** 可执行的规则、代表性资源规格和按依赖排序的任务。文档能支持当前制作即可，新增细节随验证结果补齐。

<a id="phase-3"></a>
## 3｜用原型验证最不确定的部分

原型用较小投入回答具体问题。先写“需要知道什么”，再决定做纸面流程、灰盒场景、交互草图还是短程序。原型可以拆成玩法、视觉和技术几种，各自给出结论。

| 验证目标 | 最小尝试 | 观察内容 |
| --- | --- | --- |
| 玩家理解 | 一段完整交互，用临时图像与文字 | 能否发现入口、理解反馈并决定下一步 |
| 操作手感 | 一个角色、一种操作、少量障碍 | 输入、动作和碰撞是否符合预期 |
| 叙事节奏 | 一个有前提和结果的事件 | 选择是否有可理解的差异，文字是否打断行动 |
| 画面可读性 | 一个代表性镜头，使用目标显示尺寸 | 轮廓、层次、文字和交互物是否清楚 |
| 技术可行性 | 最困难的资源或设备条件 | 能否导出、加载、运行、保存和恢复 |

**三个起点可以放在一起看：**

| 项目 | 早期形态 | 可以学到的验证方式 |
| --- | --- | --- |
| [《Splatoon》](https://www.nintendo.com/en-gb/Games/Wii-U-games/Splatoon-892510.html) | 任天堂访谈中的黑白方块喷墨、争夺地面原型 | 先让核心规则可玩，再发展角色形象。[4](#ref-4) |
| [《Baba Is You》](https://www.hempuli.com/baba/) | 作者保留的 Nordic Game Jam 2017 版本 | 用小规模可玩谜题呈现规则变化，再扩充规则组合与内容。[5](#ref-5) |
| [《A Short Hike》](https://ashorthike.com/) | 作者暂缓大项目后开始的新原型 | 原型也可以帮助重新选择一个与当前资源相符的项目。[1](#ref-1) |

原型结束时，给出继续、修改或停止的决定。例如“玩家理解观察与回应，但按钮位置使多数人漏看”，接下来应改信息呈现，再验证；“手机上核心模型无法在目标条件下运行”，则需要比较简化资源、固定镜头或改变技术路线。

试玩时先给情境和目标，让玩家自行操作，记录停顿、误解与选择。解释之后才会玩的部分，也应记下解释内容。最后再问他们以为发生了什么，与原本设计作比较。个人或少量试玩能发现问题，但不足以代表所有目标玩家。

**阶段成果：** 原型、验证问题、实际观察和下一步决定。临时程序与资源是否沿用，取决于后续的维护和品质要求。

<a id="phase-4"></a>
## 4｜做一段能够代表成品的制作样板

垂直切片（Vertical Slice）是一小段贯通主要环节、接近目标品质的体验。它让你同时检查效果、交接和生产速度：规则、美术、声音、界面、存档怎样一起工作，一段内容完成后还能否经济地修改。

选择有代表性的困难。例如，渡轮对话游戏可以选一段包括角色动作、背景变化、长对白、一次选择和重新进入的场景；使用手机与多语言时，把这些条件也放进样板。只选最短文字和最容易的镜头，会低估后续成本。

<a id="visual-production"></a>
### 同样是二维画面，制作路径可以很不同

| 游戏 | 有资料支持的制作路径 | 由此需要考虑的生产问题 |
| --- | --- | --- |
| [《Hollow Knight》](https://www.hollowknight.com/) | Photoshop 中的手绘与传统动画 → PNG → Unity | 分层、动作帧、尺寸与导入后的显示一致性。[6](#ref-6) |
| [《Cuphead》](https://cupheadgame.com/) | 纸上绘制动画 → Photoshop 上色 → Unity | 绘制、扫描与整理、上色、接入是连续工序，改动作会影响多处。[7](#ref-7) |
| [《Dead Cells》](https://dead-cells.com/) | 三维模型与骨架动作 → 低分辨率渲染 → 图像帧进入游戏 | 动作可以从三维源工程反复调整，还要检查小尺寸下的轮廓与像素闪烁。[8](#ref-8) |

这些记录说明，美术风格、制作工具和运行形式需要分别确认。你也可以用 Blender 制作固定镜头，再输出背景图；若允许玩家任意绕到物体背后，运行端就需要支持那些视角及其资源。

样板完成后，再做第二个同类对象或场景，记录新增内容实际用了多久。第一次往往包括摸索工具和建立规则；第二次更能揭示复用程度。复杂角色、普通道具和远景物件应分别估算，不能只取最简单对象的速度。

<a id="milestones"></a>

| 名称 | 用途 | 完成时应能证明什么 |
| --- | --- | --- |
| 原型 Prototype | 检验一个或几个假设 | 这个操作、规则或技术方案是否值得继续 |
| 垂直切片 Vertical Slice | 验证目标品质和完整制作方法 | 能否按这个标准持续做下去 |
| Demo／试玩版 | 让特定受众体验作品 | 当前展示范围能否独立运行并形成合理预期 |
| MVP／最小可行产品 | 用较小产品检验价值等假设 | 预先设定的产品假设是否得到支持 |

同一个版本可以承担多种用途。展示给发行方的 Demo、内部测试原型和公众试玩版，各自的受众、完成条件与可接受问题仍应写清。

**阶段成果：** 一段目标品质的完整体验、可复用源文件、交接规格、实际工时和主要返工点。

<a id="phase-5"></a>
## 5｜按稳定方法制作与接入内容

正式制作把已经验证的规则和流程扩展成完整作品。每轮选一组有限任务，完成制作、接入、检查，再留下可玩的版本。这样可以及早发现“资源很多，游戏却没有向前推进”的情况。

一条常见的资源流程是：**参考与设计 → 源工程 → 导出文件 → 导入游戏 → 设置规则和显示 → 在实际场景检查。** `.blend` 或分层绘图文件保存编辑能力，PNG、GLB、音频等承接导出，游戏中还要补上触发、碰撞和状态连接。文件交接见 [002 的格式速查](posts-2026-umwelt-game-development-handbook-002.html#formats)。

### 系统工作与内容工作分别估算

| 作品中的例子 | 可复用的系统 | 持续增加的内容 | 容易增加成本的变化 |
| --- | --- | --- | --- |
| [《星露谷物语》](https://www.stardewvalley.net/)式种植 | 时间、物品、种植与收获规则 | 作物、图像、价格与描述 | 新作物引入全新的生长或交互机制 |
| [《Hollow Knight》](https://www.hollowknight.com/)式探索 | 移动、战斗、门与存档 | 房间、敌人、动画与环境 | 新能力改变旧地图的可达性 |
| [《Papers, Please》](https://papersplea.se/)式检查 | 证件展示、规则判断与裁决 | 来访者、证件、事件与对白 | 新规则与已有规则产生大量组合 |
| [《80 Days》](https://www.inklestudios.com/80days/)式旅程 | 路线、资源和条件叙事 | 城市、事件与选择 | 新状态影响此前已经写好的段落 |

这是用于估算的玩法拆分，不代表这些作品的实际代码结构。增加内容时，如果需要新的状态、输入或存档字段，就把它单列为系统任务，再核对已有内容。

### 让任务能交接、能验收

“把场景做精致”缺少终点。可以改为：“保留镜头和已有布局，完成一张目标尺寸背景；桌椅轮廓在实际显示尺寸清楚，人物与地面有接触关系；交付可编辑源工程和导出图，并在游戏入口检查。”

每项任务保留五项即可：**目的、范围、依赖、完成条件、验证材料**。版本管理记录修改；任务看板记录谁在做什么；可玩的构建用于共同检查。个人项目也可以用同样的结构，把记录缩短。

委托开发者、外包或 AI 时，交付对象仍是文件与实际效果。需要源工程就写明源工程，需要上线就写明公开入口。收到“已实现”后，继续核对运行版本、执行过的检查和尚未验证的条件。

**阶段成果：** 内容持续进入可玩版本，制作问题能追溯到具体资源、规则和版本。

<a id="phase-6"></a>
## 6｜测试规则、理解、表现与性能

测试要同时覆盖“程序是否按约定工作”和“玩家能否得到目标体验”。先在制作中持续检查，到临近发布时再围绕完整成品集中验证。

| 检查层次 | 重点 | 可执行的例子 |
| --- | --- | --- |
| 规则与数据 | 条件、计算、重复执行、存档 | 同一物品能否被重复领取，读档后状态是否一致 |
| 系统连接 | 输入、动画、声音、界面协作 | 点击只触发一次事件，动画结束后正确进入下一状态 |
| 完整流程 | 开始、推进、失败、结束、再次进入 | 从正常入口走完一条路线，再退出、恢复和重开 |
| 理解与节奏 | 目标、提示、反馈、等待 | 陌生玩家是否看见可操作物，知道结果意味着什么 |
| 兼容与无障碍 | 设备、输入、语言、可读性、替代反馈 | 长文本与大字号不遮挡按钮，声音信息有必要的视觉对应 |
| 性能 | 加载、帧耗时、内存和长时间运行 | 在目标设备连续切场景，观察卡顿、内存和资源释放 |

自动化适合重复检查规则和流程；试玩适合观察理解与行为；截图、录屏和实际操作帮助检查画面。模拟手机尺寸能发现布局问题，实际手机仍可能出现不同的性能、输入或声音行为。[9](#ref-9)

### 同一个“难”，可能来自不同原因

| 例子 | 需要区分的情况 | 可借鉴的处理方向 |
| --- | --- | --- |
| [《Celeste》](https://www.celestegame.com/) | 玩家意图正确，但按键时刻与位置略有偏差 | 作者说明了离开边缘后的短暂跳跃机会、落地前输入缓冲和边角修正，使操作更贴近意图。[10](#ref-10) |
| [《Hades》](https://www.supergiantgames.com/games/hades/) | 玩家想继续体验，但承受伤害的压力过高 | God Mode 提供减伤，并随死亡提高耐受；这是公开可选的难度辅助。[2](#ref-2) |
| [《Baba Is You》](https://www.hempuli.com/baba/) | 玩家尚未理解当前文字规则如何组合 | 试玩应优先检查规则信息和反馈，再判断谜题是否需要调整 |
| [《Return of the Obra Dinn》](https://obradinn.com/) | 玩家暂时缺少或误读证据 | 检查线索的可见性与推理条件，保留重新调查的途径 |

后两项是根据玩法作出的测试分析。它们与前两项并列，是为了区分操作、承受压力、规则理解与信息推断。只有先定位困难来自哪里，修改才会对准问题。

### 性能用测量定位

卡顿可能来自程序计算、图形绘制、资源读取或内存回收。先在目标设备复现，再用分析工具查看开销。60 帧每秒对应平均每帧约 16.7 毫秒，30 帧约 33.3 毫秒；实际还要看耗时波动，平均帧率无法单独说明卡顿。

比较优化前后时固定镜头、输入、资源、画质和设备。先找最大开销，再改模型、贴图、计算或加载方式，并检查视觉与交互有没有损失。

<a id="acceptance"></a>
### 问题记录与验收

一份可用的问题记录包括：版本、环境、起始状态、复现步骤、预期、实际、证据和出现频率。把观察到的现象与原因猜测分开，调查者才能检验解释。

修复后先复测原问题，再检查受影响的周边流程（回归测试）。例如修了跳过对白，要同时检查快速连点、自动播放、选择菜单和读档。严重程度描述影响，优先级决定处理顺序；丢失存档、无法启动和必经流程卡死通常需要优先处理。

发布前可以采用这份验收清单：

- 从正常入口完成主要流程，失败、取消、返回和重试都有结果。
- 新存档、旧存档、无存档与恢复失败按约定处理。
- 目标设备、输入和语言已检查，未覆盖部分明确记录。
- 图像、声音、字体和外部资源随成品正确交付。
- 性能达到项目目标，长时间运行没有已知的阻断问题。
- 修复已经复测，检查结果对应当前候选版本。

**阶段成果：** 可以说明“哪个版本，在什么条件下，通过了哪些检查”，据此决定发布或继续修复。

<a id="phase-7"></a>
## 7｜发布经过检查的实际成品

发布包括生成文件、安排分发、准备页面与说明、检查玩家实际取得的结果。保存代码、上传仓库、部署网站与玩家能正常游玩是连续但不同的步骤。

| 交付方式 | 需要额外检查的环节 |
| --- | --- |
| 网页 | 公开网址、资源路径、加载失败、触屏、浏览器声音策略和本地存储 |
| 桌面下载 | 解压或安装、首次启动、操作系统与图形支持、存档路径 |
| 商店 | 产品页、实际构建、系统要求、平台接入、审核与发布时机 |
| 抢先体验 | 当前可玩范围、未完成部分、反馈渠道和持续更新能力 |

Steam 的商店页与游戏构建分别接受审核，因此图片、描述和程序应分别准备，再核对它们是否一致。[11](#ref-11) 网页音频可能需要玩家手势才能开始；`localStorage` 与网站来源和浏览器有关，清除站点数据也可能删除进度。[12](#ref-12), [13](#ref-13)

### 用三个发布案例检查不同风险

- **[《Baldur’s Gate 3》](https://baldursgate3.game/)**：2023 年 Hotfix 4 在通过测试后，为更改版本号又重新构建，出现编译问题；回退期间，部分新存档无法由旧版本继续读取。Larian 随后说明会让候选版本的任何更改重新经过完整检查。这个事件强调测试文件、发布文件和存档兼容之间的关系。[14](#ref-14)
- **[《Hades》](https://www.supergiantgames.com/games/hades/)**：抢先体验期间持续发展战斗与故事，再进入 1.0。此类交付要同时维护当前版本和之后的制作计划。[2](#ref-2)
- **[《星露谷物语》](https://www.stardewvalley.net/)**：PC 版 1.5.5 从 XNA 迁移到 MonoGame，并包含兼容与修复工作。底层技术更新可能改变运行条件，即使内容变化不大，也需要安排验证。[15](#ref-15)

确定候选版本后，保存对应源代码、依赖和构建产物，检查最终包或站点。发布完成，再从公开入口重新下载或访问。回退时同时考虑程序与玩家数据；新版本写入的数据未必能直接由旧版本读取。

**阶段成果：** 公开入口、实际发布版本、检查结果，以及上一稳定版本和必要的恢复方法。

<a id="phase-8"></a>
## 8｜维护、扩展与结束支持

收到反馈后，先分清缺陷、理解困难、设备差异、偏好和新增需求。分别复现或观察，再决定处理。一次反馈提出的解决办法可以作为线索，优先弄清它试图解决什么问题。

补丁优先处理启动、存档和必经流程；体验调整需要重新试玩；新增内容则重新经过范围、依赖和生产估算。规则变化后检查已有内容，数据结构变化后检查旧存档，运行环境升级后检查构建和目标设备。

维护也包括结束。小作品完成后，可以停止扩展，保留可运行成品、源文件、依赖版本、资源来源、制作与导出说明，以及必要备份。依赖在线服务的作品，还需要决定服务结束后哪些内容仍然可用。

**阶段成果：** 可解释的维护范围，以及未来能够重新打开、导出和交付的项目。

<a id="cost"></a>
## 预算与进度：从样板估算剩余工作

总成本包括制作、接入、返工、测试、发行和维护。软件免费时，这些工作仍然存在。预算至少覆盖人力、软件与素材、设备、外包、本地化、宣传、平台或服务、维护预留。

可以先按资源类型估算：

**剩余工作 ≈ 同类内容数量 × 已测得的单项工时 ＋ 共用系统 ＋ 整合测试 ＋ 返工与发布预留。**

这是计划框架。不同复杂度的内容应分组；并行工作受人员和依赖限制；“工作天数”与“日历截止日期”也要分开。例如，一个场景的动作要等角色设计确定，增加程序人手未必能缩短这段等待。

| 制作选择 | 主要增加的工作 |
| --- | --- |
| 多一个角色 | 设定、图像或模型、动作、声音、对白与互动组合 |
| 多一种语言 | 翻译、校对、字体、布局、语境和版本同步 |
| 多一个平台 | 输入、性能、构建、发行流程和设备测试 |
| 固定镜头改自由视角 | 背面与遮挡、实时光照、相机、模型和性能 |
| 单机改实时联机 | 同步、权威状态、网络异常、服务与多人测试 |
| 增加一种永久分支 | 后续文本、状态、存档与组合验证 |

画面规模、文本数量和系统复杂度可以互相转移成本。前面的《Cuphead》《Dead Cells》《Papers, Please》分别把大量工作放在动画生产、可调整的资源流程和规则与文本组合上。比较项目时，应比较这些工作构成，再参考团队人数与工期。

<a id="terms"></a>
## 常用术语速查

| 术语 | 在项目中的含义 |
| --- | --- |
| 机制 Mechanic／核心循环 Core Loop | 一项具体规则与操作关系／反复出现的行动、反馈和选择结构 |
| 范围 Scope／里程碑 Milestone | 本次承诺的内容与品质／有明确成果的检查点 |
| 管线 Pipeline／依赖 Dependency | 内容从制作到使用的步骤／完成某项工作所需的前提 |
| 资源 Asset／构建 Build | 图像、模型、声音等内容／生成成品的过程或所生成的版本 |
| Alpha／Beta | 团队约定的成熟阶段；应另写清功能、内容与质量条件 |
| 功能齐备／内容齐备 | 约定能力已实现／计划内容已接入；之后仍需检查与打磨 |
| QA／测试／试玩 | 质量过程与风险管理／检查具体结果／观察玩家理解与体验 |
| 冒烟测试／回归测试 | 快速检查关键路径／修改后检查已有行为是否受影响 |
| 阻断问题／软锁 Softlock | 阻止必要推进的问题／程序仍运行但玩家无法继续 |
| 性能分析 Profiling | 测量执行时间、内存和图形等开销以定位问题 |
| 重构 Refactoring／技术债务 | 调整内部组织并保留约定行为／增加后续修改负担的问题 |
| RC／补丁 Patch／回退 Rollback | 候选发布版本／修复或调整／恢复之前的程序或配置并处理数据 |
