# 游戏程序与运行原理手册｜ChatGPT 写给五月七日的指导笔记 003

**理解系统的职责与连接 · 撰写：ChatGPT · 2026-10-13**

玩家作出选择后，游戏先接收操作，再依据规则更新记录，最后通过文字、画面或声音呈现结果。这几步连起来，就构成了一次基本的交互。角色持续移动、环境随时间变化时，程序也会更新相应状态，因此游戏通常由玩家操作与时间共同推动。[1](#ref-1)

你可以把具体实现交给开发者或 AI，同时保留对设计和结果的判断。为此，首先需要理解各个系统负责什么，以及一项修改会影响哪些部分。因此，本篇重点解释运行原理、实现取舍和验收要求；代码语法留待需要亲自编程时再学习。

<a id="runtime"></a>
## 1｜制作阶段与运行阶段

制作期间，项目里会保留源图、设计记录、测试资料和程序文件。玩家游玩时只需要其中负责运行的部分，因此发布流程会从项目中整理或生成一份成品。引擎项目通常通过构建或导出完成这一步；网页项目也可能在发布前处理字体、压缩资源和配置。[2](#ref-2), [9](#ref-9)

| 概念 | 解释 | 制作时需要确认的内容 |
| --- | --- | --- |
| 源文件 | 用于制作和修改的原始内容，例如源图、代码和场景工程 | 保留足以继续编辑的版本 |
| 构建产物 | 按发布配置生成的可交付文件 | 验证实际准备发布的这一份成品 |
| 运行环境 | 执行成品的系统，例如浏览器或目标平台的运行组件 | 明确玩家所需的系统、设备和权限 |
| 内存中的状态 | 程序运行期间保存的信息 | 找出退出后仍需保留的部分 |
| 存档 | 为下次恢复而持续保存的数据 | 约定重载后从哪一步继续 |

有些游戏直接使用浏览器提供的绘图、音频、输入和存储能力，再由项目自己的程序组织玩法。以你正在做的[《等足目赋格》](https://umwelt.fivsevn.com/isopoda/)网页版为例，它采用的就是这条路线：Canvas 2D 提供二维绘图接口，JavaScript 模块处理观察、交互和进度。这样可以省去通用游戏引擎的整套工作流程，同时继续利用浏览器已有的基础能力。[3](#ref-3), [4](#ref-4), [8](#ref-8)

因此，**制作工具用于编辑内容，运行环境用于执行成品，项目程序则把基础能力组织成具体玩法。** 三者的分工明确后，就可以理解一款游戏为何能够采用不同的工具组合。

<a id="state"></a>
## 2｜输入、规则、状态与反馈

假设我们为你的观察游戏增加一个“保持距离”选项，可以把一次选择拆成下面几个环节（这是用于说明原理的设计示例）。

| 环节 | 负责的内容 | 需要明确的边界 |
| --- | --- | --- |
| 输入 | 接收点击、触摸或按键 | 操作落在哪个对象上，是否允许重复输入 |
| 条件检查 | 判断操作当前是否有效 | 资源是否就绪，观察是否已经结束，前提是否满足 |
| 规则执行 | 计算这次操作带来的结果 | 哪些记录或环境参数会改变 |
| 状态更新 | 保存变化后的情况 | 当前进入反馈阶段，还是继续等待选择 |
| 表现更新 | 显示文字、动作、声音和界面变化 | 玩家如何察觉这次选择的结果 |
| 持久保存 | 将需要保留的进度写入存档 | 立即退出后能否恢复这次结果 |

这里，输入描述玩家做了什么，规则决定操作的后果，状态保存结果，反馈再把结果传达给玩家。它们之间需要接通：按钮可以先播放按下动画，但选择记录可能尚未写入；也可能记录已经改变，界面却还没有更新。遇到这种情况，就应分别检查操作是否被接收、规则是否执行，以及反馈是否显示。

**[《Celeste》](https://www.celestegame.com/)的跳跃处理体现了输入与规则的区别。** 开发者 Maddy Thorson 介绍，玩家在落地前稍早按住跳跃键，游戏可以暂时保留这次输入，并在落地时执行跳跃。也就是说，按键到达的时刻与动作执行的时刻可以分开安排，从而使操作更符合玩家意图。[11](#ref-11)

为了安排这些阶段，程序可以采用“状态机”：先定义等待选择、显示反馈、结束等状态，再规定每个状态允许的操作和转换条件。这是一种组织逻辑的方法，可以由项目代码或现成工具实现。[5](#ref-5) 你需要确定的是各阶段的行为与转换条件，具体写法则由实现者选择。

同样，条件不满足时也需要有明确结果，例如暂时禁用按钮、说明原因或允许返回。把这些情况与正常结果一起写清楚，开发者才有完整的规则可执行。

<a id="modules"></a>
## 3｜内容、数据与模块

数据记录对象和当前情况，程序规定怎样处理这些信息。例如，一组数据可以记录角色名字、位置和姿态，而程序根据它们生成画面。对白与关卡布置也可以独立保存，以便内容修改时继续使用原有的处理逻辑。这种分工常称为“数据驱动”。[2](#ref-2)

| 名词 | 定义与解释 |
| --- | --- |
| 变量 | 在运行过程中保存某项信息，例如当前观察次数 |
| 对象 | 将相关信息组织为一个整体，例如某只动物的位置、形态和状态 |
| 函数 | 完成一项处理的程序单元，例如检查当前是否允许继续 |
| 模块 | 承担一组相关职责的程序部分，例如存档、音频或语言显示 |
| 接口 | 模块约定的输入、输出与调用方式，例如向音频系统提供当前场景状态 |
| 依赖 | 一个模块正常工作所需要的其他模块、数据或工具 |

理解这些名词后，可以按职责阅读项目：先找到叙事、界面和存档分别由哪些部分负责，再查看它们怎样交换信息。至于一个模块放在一个文件还是拆成多个文件，属于组织方式，可以随着项目规模调整。

以你的对话界面为例，叙事模块决定下一段内容，本地化模块提供当前语言的文本，界面模块负责显示。修改一条台词通常沿用原有显示方式；新增一种选择方式则可能同时涉及叙事、输入和布局。因此，**内容扩展主要增加具体材料，功能扩展主要改变系统能够支持的行为**，两者需要分别估算工作量。

<a id="time"></a>
## 4｜游戏时间、逻辑更新与画面更新

程序会反复安排输入处理、状态更新和画面显示，这种持续运行的组织方式通常称为游戏循环。网页游戏的循环还要借助浏览器调度：浏览器安排程序何时执行，游戏再决定执行哪些更新。[1](#ref-1), [5](#ref-5)

| 时间或频率 | 含义 | 与其他部分的关系 |
| --- | --- | --- |
| 现实时间 | 设备计时所经过的时间 | 游戏可以按相同速度推进，也可以加速、暂停或按回合推进 |
| 游戏时间 | 游戏规定的时间进度 | 由规则决定怎样变化，可以与现实时间分开 |
| 逻辑更新 | 计算位置、条件或环境变化 | 更新结果交给显示系统使用 |
| 帧率 | 单位时间内生成或呈现画面的频率 | 影响显示连续性，还需结合操作延迟等因素评价体验 |
| 动画节奏 | 角色姿态和动作变化的时机 | 可以按美术需要安排，与整体显示频率分别控制 |

**[《Cuphead》](https://cupheadgame.com/)提供了直观的例子。** Unity 的制作访谈说明，角色手绘动画采用每秒 24 帧的节奏，而游戏以每秒 60 帧运行。两项安排服务于不同目标：前者保持传统动画的视觉感受，后者服务于交互响应。[10](#ref-10) 因而，讨论“帧率”时需要先说明是在谈角色动画、画面显示还是逻辑更新。

类似地，你的鼠妇可以持续活动，而文字观察等待玩家选择；打开菜单时，也可以只暂停环境模拟，继续显示按钮动画。设计中需要分别规定这些行为，实现者才能明确哪些系统继续运行、哪些暂时停止。

不同设备的显示能力可能不同，因此程序还需要处理更新频率与运动速度的关系。验收时，应比较同一动作在目标设备上的速度、等待时长和操作结果，再评价画面是否流畅。[1](#ref-1)

**逻辑更新决定世界发生什么，画面更新负责把结果呈现出来。** 对你的观察作品，可以先保证行为、文字与反馈一致，再决定需要多少持续动画来支撑氛围。

<a id="persistence"></a>
## 5｜加载、存档与恢复

打开网页后，页面结构、字体、声音和场景数据可能分批到达。于是，玩家已经看见界面时，某些资源仍可能在加载。项目需要据此规定加载期间允许哪些操作，并为失败情况提供提示或重试方式。

保存进度时，程序记录的是以后恢复游戏所需的信息，例如当前场景、已完成事件和对象标识。再次进入后，游戏读取这些记录，再恢复规则与画面。既然画面可以根据状态重新生成，就可以只保存恢复必需的数据，而把能够可靠重算的显示细节留给运行程序。[6](#ref-6)

| 需要区分的内容 | 解释 |
| --- | --- |
| 自动保存／手动保存 | 区分保存时机；数据存放在本地还是云端，需要另行确定 |
| 本地存档／云存档 | 区分保存和同步位置；不同程序版本能否读取，仍由兼容方案决定 |
| 随机结果／随机种子 | 前者是已经产生的结果，后者是生成序列的起点；跨版本重现还取决于算法等条件 |
| 版本迁移／重新开始 | 前者转换已有进度，后者建立新的游戏状态 |
| 程序回退／数据恢复 | 前者换回旧程序，后者处理已有数据；需要确认旧程序能否读取后来生成的存档 |

**[《Factorio》](https://www.factorio.com/)将恢复目标写成了明确要求。** 开发者在存取档说明中提出，在外部条件保持不变时，保存、退出和重新加载应保持可观察行为一致。为达到这一目标，他们还要处理版本变化、模组变化与无效数据。[6](#ref-6) 从目标到技术工作的关系在这里很清楚：先决定重载后应保留什么，再安排保存、迁移与验证（案例依据 2018 年的开发记录）。

对你自己的游戏，也可以采用同样的表达顺序：先明确保存时机和恢复位置，再列出需要保留的选择、环境与记录。这样，“存档完成”就有了可以实际检查的含义。

<a id="network"></a>
## 6｜单机、网页托管与联机

网页托管服务把文件交给浏览器，浏览器随后可以在本地执行规则。若游戏还需要账号、匹配或多人共同活动，再增加相应远端服务。因此，网页访问方式与多人联机功能需要分别描述。静态托管也可以分发会变化、可操作的网页；这里的“静态”描述服务器提供文件的方式。[9](#ref-9)

| 部分 | 主要职责 |
| --- | --- |
| 浏览器客户端 | 在玩家设备上显示画面、接收输入并执行程序 |
| 文件托管 | 向访问者提供网页、图像和声音等文件 |
| 应用服务器 | 处理账号、匹配、对战判定等远端任务 |
| 数据库 | 保存和查询需要持续保留的数据 |
| 网络同步 | 交换输入或状态，使参与者对共同世界的记录保持一致 |

**[《Factorio》](https://www.factorio.com/)的多人系统展示了一种同步方式。** 开发团队介绍的确定性锁步方案交换玩家输入，各端按照相同规则推进模拟；如果结果出现差异，就会失步。[7](#ref-7) 因此，联机设计需要明确交换什么信息、由谁计算，以及出现差异时怎样恢复（这里说明的是 2017 年开发记录中的方案；其他游戏可以采用不同结构）。

对存在竞争、账号资产或交易的项目，还需要确定由哪个可信系统确认结果。这些安排会影响服务器费用、隐私和故障处理，应与玩法一起考虑。

<a id="isopoda"></a>
## 7｜回到你正在做的《等足目赋格》

把上面的概念放回你的网页版，就可以得到下面这张对应表。实际实现以参考资料中固定的仓库版本为准，后续修改时再对照当前文件。[8](#ref-8), [9](#ref-9)

| 本篇概念 | 你的游戏中的对应 |
| --- | --- |
| 输入与界面 | 网页按钮和交互模块接收选择、点击与拖动 |
| 状态与规则 | 逻辑模块维护观察进度、环境状态和反馈 |
| 内容数据 | 观察文本、事件、物种和环境资料分别维护 |
| 画面生成 | Canvas 2D 组合场景，角色依据形态和姿态参数生成像素 |
| 声音反馈 | 共享音频模块调用 Web Audio，处理音乐、音效和音量 |
| 持久保存 | 网页主游戏将进度写入浏览器本地存储 |
| 开发验证 | Node.js 测试和浏览器检查分别验证相应范围 |
| 文件发布 | 发布流程准备站点资源，由 Pages 分发给访问者 |

你可以把这条路线概括为“浏览器基础能力＋项目专用的 JavaScript 模块”。以后即使改用通用引擎，仍然需要安排输入、状态、显示和保存，只是部分职责可以交给引擎已有的系统处理。

<a id="cost"></a>
## 8｜软件成本与制作判断

下面把软件使用费用与开发工作分开列出，便于判断成本落在哪里。费用形式沿用 **2026-10-13** 的资料记录；采购时需再查看对应版本与使用条件。完整比较见 [002](posts-2026-umwelt-game-development-handbook-002.html#cost-legend)。

| 技术或工具 | 开放情况 | 费用与使用范围 |
| --- | --- | --- |
| JavaScript、HTML、CSS、Canvas、Web Audio | 语言或网页接口 | 使用这些标准本身没有制作软件许可费；设备、素材和实现工作另计。[3](#ref-3), [4](#ref-4) |
| [Node.js](https://nodejs.org/en/about)、[Playwright](https://playwright.dev/) | 开源工具 | 软件免费，测试设备和云端执行资源可能收费 |
| [Unity](https://unity.com/products) | 专有软件 | 符合条件的免费方案，以及适用的付费席位方案 |
| [Godot](https://godotengine.org/license/) | 开源，MIT | 引擎免费，平台适配、服务与人力另计 |
| [Git](https://git-scm.com/about)／[GitHub](https://github.com/pricing)／[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) | Git 开源；后两者是托管服务 | Git 免费；托管按实际方案、适用范围与额度计费 |

使用现成引擎，可以减少部分系统的自建工作，同时也需要学习和适配它的组织方式。编写专用系统则更便于围绕作品安排结构，但维护责任也留在项目中。因此，比较两条路线时，应一起估算许可、接入、制作与维护，而只把购买金额作为其中一项。

交付一项新需求时，你可以明确五件事：哪些状态改变、允许哪些操作、玩家看见什么反馈、怎样保存和恢复、在哪些环境验证。例如增加“等待”选项，就要说明等待是否推进时间、能否中断以及重载后从哪里继续。有了这些约定，实现者便能选择合适的方法，你也能据此检查结果。

## 参考文献与学习资源

以下以作者教材、开发团队记录与官方英文文档为主。每项注明阅读重点，使你可以先理解系统关系，再按需要深入（网页查阅日期：2026-10-13；自己的项目资料固定到提交 `0bbe083`，用于说明实现）。

<a id="ref-1"></a>
**[1] MDN contributors. _Anatomy of a Video Game_.** [英文文档](https://developer.mozilla.org/en-US/docs/Games/Anatomy)。免费。先读输入、更新与显示的概述；其中的代码示例可留作后续查阅。

<a id="ref-2"></a>
**[2] Gregory, Jason. _Game Engine Architecture_，第 4 版.** [作者官网](https://www.gameenginebook.com/)。英文，两卷本，书籍购买或借阅，官网概览免费。重点看系统分工、资源与工具链；适合在需要进一步认识整体架构时查阅。

<a id="ref-3"></a>
**[3] MDN contributors. _Canvas API_.** [英文文档](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API)。免费。先了解画布提供哪些绘图能力，再与引擎的功能范围比较。

<a id="ref-4"></a>
**[4] MDN contributors. _Web Audio API_；_Window: localStorage Property_.** [音频](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API) · [本地存储](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)。英文，免费。分别用于理解声音执行与数据保存的条件。

<a id="ref-5"></a>
**[5] Nystrom, Robert. _Game Programming Patterns_（2014）.** [作者在线版](https://gameprogrammingpatterns.com/) · [Game Loop](https://gameprogrammingpatterns.com/game-loop.html) · [State](https://gameprogrammingpatterns.com/state.html)。英文，在线全文免费，纸书等版本付费。阅读问题背景和结构说明，重点理解这些组织方式解决了什么问题。

<a id="ref-6"></a>
**[6] Wube Software. _Friday Facts #270 — HR Substation & Save/Load Overview_（2018-11-23）.** [开发团队原文](https://www.factorio.com/blog/post/fff-270)。英文，免费。阅读 Rseding 的保存与加载部分，观察恢复目标怎样转为兼容和验证要求。

<a id="ref-7"></a>
**[7] Wube Software. _Friday Facts #188 — Bug, Bug, Desync_（2017-04-28）.** [开发团队原文](https://www.factorio.com/blog/post/fff-188)。英文，免费。阅读 Twinsen 对同步与失步的说明（文中的版本问题属于当时的开发记录）。

<a id="ref-8"></a>
**[8] fivsevn. UMWELT：ISOPODA 模块说明与实现.** [模块导航](https://github.com/fivsevn/umwelt/blob/0bbe083943a4b307e38e3ea0de435d3d7864a345/isopoda/README.md) · [主程序](https://github.com/fivsevn/umwelt/blob/0bbe083943a4b307e38e3ea0de435d3d7864a345/isopoda/game.js) · [角色绘制](https://github.com/fivsevn/umwelt/blob/0bbe083943a4b307e38e3ea0de435d3d7864a345/isopoda/sprites.mjs) · [音频](https://github.com/fivsevn/umwelt/blob/0bbe083943a4b307e38e3ea0de435d3d7864a345/assets/audio/audio-engine.mjs)。用来定位你自己的实现；先看模块说明即可。

<a id="ref-9"></a>
**[9] fivsevn. UMWELT：验证与发布说明.** [发布](https://github.com/fivsevn/umwelt/blob/0bbe083943a4b307e38e3ea0de435d3d7864a345/isopoda/docs/deployment.md) · [测试](https://github.com/fivsevn/umwelt/blob/0bbe083943a4b307e38e3ea0de435d3d7864a345/tests/README.md)。用来比较制作、验证和玩家运行三个环境的职责。

<a id="ref-10"></a>
**[10] Unity／Studio MDHR. _Cuphead — Made with Unity_.** [制作访谈](https://unity.com/made-with-unity/cuphead)。英文，免费。动画节奏与游戏运行频率的对照，适合配合第 4 节阅读。

<a id="ref-11"></a>
**[11] Thorson, Maddy. _Celeste & Forgiveness_.** [作者文章](https://www.maddymakesgames.com/articles/celeste_and_forgiveness/index.html)。英文，免费，附动作演示。先看跳跃输入的保留与落地执行，理解操作响应怎样通过规则调整。

**阅读顺序：** 从 [1] 的概述开始，结合 [11] 的动作演示，再读 [6] 的保存案例。需要更系统的结构知识时，查阅 [2] 和 [5]。
