# 游戏程序与运行原理手册｜ChatGPT 写给五月七日的指导笔记 003

**理解系统的职责与连接 · 撰写：ChatGPT · 2026-10-13**

一款游戏的运行可以概括为：**接收操作，依据规则更新状态，再把结果呈现给玩家。** 素材、声音、界面、存档和联网系统围绕这条关系配合工作。不同游戏可以由操作、时间或两者共同推进，并不要求每一项工作都在每一帧重复执行。[1](#ref-1)

本篇不介绍代码语法。重点是让项目负责人能够区分需求影响的系统、理解实现中的取舍，并提出可检查的要求。

<a id="runtime"></a>
## 1｜制作阶段与运行阶段

开发者操作的项目文件，与玩家收到的成品不是同一个范围。项目可能包含源图、设计记录、测试资料和制作工具；发布时，只交付目标运行环境需要的部分。引擎项目还会经过导出或构建，网页项目也可能处理字体、压缩资源和配置。[2](#ref-2)[9](#ref-9)

| 概念 | 解释 | 项目判断 |
| --- | --- | --- |
| 源文件 | 用于制作和修改的原始内容，例如源图、代码和场景工程 | 是否保留了可继续编辑的版本 |
| 构建产物 | 按发布配置生成的可交付文件 | 测试对象是否就是准备发布的这一份 |
| 运行环境 | 执行成品的系统，例如浏览器或目标平台的运行组件 | 玩家需要什么系统、设备和权限 |
| 内存中的状态 | 当前运行过程里保存的信息 | 退出后需要保留的内容是否已另行保存 |
| 存档 | 为下次恢复而持久保存的数据 | 恢复后应继续哪一段体验 |

**制作工具负责产出和修改内容，运行环境负责执行成品。** 没有使用通用游戏引擎，不代表没有使用底层能力；原生网页游戏仍然依赖浏览器提供的绘图、音频、输入和存储接口。[3](#ref-3)[4](#ref-4)

<a id="state"></a>
## 2｜输入、规则、状态与反馈

以下是一项演示性需求，不是对某个现有关卡的描述：玩家选择“保持距离”，游戏记下这次选择，并呈现相应观察结果。

| 环节 | 负责的内容 | 需要明确的边界 |
| --- | --- | --- |
| 输入 | 接收点击、触摸或按键 | 点中了哪个对象；是否允许连续操作 |
| 条件检查 | 判断操作当前是否有效 | 是否仍在加载、是否已结束、是否满足前提 |
| 规则执行 | 计算这次操作带来的结果 | 影响哪些记录、关系或环境参数 |
| 状态更新 | 保存当前已经发生的变化 | 当前处于选择、反馈还是结束阶段 |
| 表现更新 | 显示文字、动作、声音和界面变化 | 玩家能否理解发生了什么 |
| 持久保存 | 将需要保留的进度写入存档 | 立即退出后能否恢复这次结果 |

**输入表示玩家做了什么，规则决定这次操作造成什么变化，状态记录变化后的结果，反馈负责让玩家感知结果。** 按钮闪动不一定意味着选择已经被记录；反过来，数据改变但没有反馈，也可能使玩家以为操作无效。

“状态机”是一种组织阶段的方式。例如“等待选择 → 显示反馈 → 等待下一次选择”，每个阶段规定允许的操作。它不是必须购买的软件，而是避免流程混乱的一种结构。[5](#ref-5) 是否采用这种组织方式可以交给实现者，项目负责人需要确定的是：每个阶段允许什么，什么条件可以进入下一阶段。

失败处理同样属于规则。对无法执行的操作，可以禁用、解释原因或提供替代行为；不能只规定成功时的表现。

<a id="modules"></a>
## 3｜内容、数据与模块

数据描述对象和当前情况，程序描述怎样处理这些情况。对白、物种参数和关卡布置可以保存在不同形式的数据中，并不要求全部采用某一种文件格式。采用“数据驱动”意味着把适合独立维护的内容与通用处理逻辑分开，不意味着不再需要程序。[2](#ref-2)

| 名词 | 定义与解释 |
| --- | --- |
| 变量 | 运行过程中保存某项信息的位置，例如当前观察次数 |
| 对象 | 将相关信息组织为一个整体，例如某只动物的位置、形态和状态 |
| 函数 | 完成一项处理的程序单元，例如检查当前是否允许继续 |
| 模块 | 承担一组相关职责的程序部分，例如存档、音频或语言显示 |
| 接口 | 模块约定的输入、输出与调用方式，例如向音频系统传入当前紧张程度 |
| 依赖 | 一个模块正常工作所需要的其他模块、数据或工具 |

这些概念用于理解分工，不要求逐一学习写法。一个文件也不必等于一个完整系统；文件数量不能直接说明项目规模或质量。

例如，叙事模块可以决定下一句文字，界面模块负责显示文字，本地化模块提供相应语言。修改台词通常不需要重写界面，但如果新增一种选择方式，就可能同时影响叙事结构、输入和布局。

**内容扩展是在既有结构中增加具体内容；功能扩展是在改变结构能够支持的行为。** 制作估算应先区分这两者，而不是把“多一句话”和“多一种交互”都当作同样的小改。

<a id="time"></a>
## 4｜游戏时间、逻辑更新与画面更新

游戏循环是持续安排输入、更新和显示的组织方式。它与浏览器处理各种任务的事件循环不是同一个概念；网页游戏是在浏览器提供的调度机制中安排自己的更新工作。[1](#ref-1)[5](#ref-5)

| 时间或频率 | 含义 | 不能直接等同于 |
| --- | --- | --- |
| 现实时间 | 设备计时所经过的时间 | 故事中一定经过同样时长 |
| 游戏时间 | 游戏规定的时间进度 | 屏幕每刷新一次就必须推进一步 |
| 逻辑更新 | 计算位置、条件或环境变化 | 每次都必须生成一幅新画面 |
| 帧率 | 单位时间内呈现画面的次数 | 操作响应、网络状态或规则正确性的全部表现 |
| 动画节奏 | 姿态和画面变化的时机 | 游戏整体计算频率 |

角色可以持续活动，而对白等待玩家选择；暂停菜单可以停下模拟，但保留按钮动画。这样的区别需要在设计中说明，不能把“暂停”默认理解为所有系统同时停止。

帧率越高不应自动意味着角色移动越快。实现者需要处理时间与更新之间的关系；负责人应检查不同设备上动作速度、交互结果和等待时长是否符合约定，而不只看开发设备上的流畅程度。[1](#ref-1)

**逻辑更新决定世界发生了什么，画面更新决定何时把结果显示出来。** 对安静的观察游戏，稳定的操作与可读反馈可能比大量持续动画更重要；这是体验取舍，不是某种帧率的通用优劣判断。

<a id="persistence"></a>
## 5｜加载、存档与恢复

页面出现不代表所有资源都已经就绪。文字、字体、声音或场景数据可能分批到达，因此项目需要规定加载完成前允许哪些操作，以及加载失败时如何提示。

保存也不是截取一张画面。存档需要记录足以恢复规则与进度的信息，例如当前场景、已完成事件和稳定的对象标识；无需把所有可以重新计算的显示细节原样保存。哪些数据必须保留，应由恢复目标决定。[6](#ref-6)

| 需要区分的内容 | 解释 |
| --- | --- |
| 自动保存／手动保存 | 决定保存时机，不决定存档一定保存在本地还是云端 |
| 本地存档／云存档 | 决定数据保存和同步的位置，不代表自动具备版本兼容 |
| 随机结果／随机种子 | 已经生成的结果与用于生成序列的起点不同；仅记录种子也未必足以跨版本重现全部过程 |
| 版本迁移／重新开始 | 将旧进度转换为新结构，与丢弃旧进度创建新游戏不同 |
| 程序回退／数据恢复 | 换回旧程序，不保证它能够读取新版已经写入的存档 |

**《Factorio》案例。** 开发者在 2018 年的存取档说明中，将“外部条件不变时，保存、退出、重载不应改变可观察行为”作为明确要求，并讨论版本变化、模组和无效数据对加载的影响。[6](#ref-6) 这是一项具体项目标准，不是所有游戏都必须采用的完全相同方案。

由此可形成一个适合委托开发的要求：明确在哪些时刻允许保存，重载后应恢复到哪一步，以及旧版本存档是否仍受支持。**存档系统负责恢复约定的游戏状态，不只是证明硬盘或浏览器里出现了一个文件。**

<a id="network"></a>
## 6｜单机、网页托管与联机

“网页游戏”描述访问和运行方式，“联机游戏”描述玩家之间或玩家与服务器之间的连接关系，两者不是同义词。静态托管可以分发包含交互程序的网页，静态指服务器分发文件的方式，不是画面只能保持不动。[9](#ref-9)

| 部分 | 主要职责 |
| --- | --- |
| 浏览器客户端 | 在玩家设备上显示画面、处理输入并执行相应程序 |
| 文件托管 | 将网页、图像、声音等文件交给访问者 |
| 应用服务器 | 处理账号、匹配、对战判定等远端任务 |
| 数据库 | 保存和查询需要持续保留的数据 |
| 网络同步 | 在参与者之间交换输入或状态，使共同体验保持一致 |

**《Factorio》案例。** 开发团队曾说明其多人系统采用确定性锁步：交换控制输入，各端按相同规则推进模拟；计算结果不一致会导致失步。[7](#ref-7) 这说明联机不等于互传屏幕画面，也不等于“增加一个联网按钮”。其他游戏可以采用不同同步方式，不应据此推断所有多人游戏的内部结构。

对包含竞争和账号资产的项目，还要明确哪些结果由可信服务器确认。网络架构、隐私、服务费用和故障恢复应共同考虑，不能只检查两台电脑是否曾经连上。

<a id="isopoda"></a>
## 7｜《等足目赋格》的实际对应

以下依据 UMWELT 的固定仓库版本，说明已有实现，不表示本次重新运行了游戏测试。[8](#ref-8)[9](#ref-9)

| 本篇概念 | 本游戏的对应 |
| --- | --- |
| 输入与界面 | 网页按钮和交互模块接收选择、点击与拖动 |
| 状态与规则 | 项目逻辑模块维护观察进度、环境状态和反馈 |
| 内容数据 | 观察文本、事件、物种和环境资料分别维护 |
| 画面生成 | Canvas 2D 组合场景；角色根据形态和姿态参数生成像素 |
| 声音反馈 | 共享音频模块调用 Web Audio，处理音乐、音效和音量 |
| 持久保存 | 网页主游戏将进度写入浏览器本地存储 |
| 开发验证 | Node.js 测试和浏览器检查分别验证相应范围 |
| 文件发布 | 发布流程准备站点资源，由 Pages 分发给访问者 |

因此，这个项目采用的是**浏览器基础能力＋项目专用的 JavaScript 运行模块**。它没有采用 Unity 或 Godot 这类通用引擎，但仍然具备输入、状态、绘制、音频和保存等必要职责。更换工具可能改变实现方式，不会使这些职责自动消失。

<a id="cost"></a>
## 8｜软件成本与负责人需要确认的内容

本表区分软件使用费用与项目制作成本，标注日期为 **2026-10-13**。完整软件比较见 [002 的成本说明](posts-2026-umwelt-game-development-handbook-002.html#cost-legend)。

| 技术或工具 | 开放情况 | 费用与本篇使用范围 |
| --- | --- | --- |
| JavaScript、HTML、CSS、Canvas、Web Audio | 语言或网页接口，不是一套单独销售的制作软件 | 使用这些标准本身不收工具许可费；设备、素材和开发工作另计。[3](#ref-3)[4](#ref-4) |
| [Node.js](https://nodejs.org/en/about)、[Playwright](https://playwright.dev/) | 开源工具 | 软件免费；测试设备和云端执行资源可能另收费 |
| [Unity](https://unity.com/products) | 专有软件 | 符合条件的免费方案；其他适用方案按席位等收费 |
| [Godot](https://godotengine.org/license/) | 开源，MIT | 引擎免费；外部服务、平台适配和人力另计 |
| [Git](https://git-scm.com/about)／[GitHub](https://github.com/pricing)／[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) | Git 开源；后两者是托管服务 | Git 免费；托管有免费适用范围、额度与付费方案 |

选择现成引擎可能减少某些系统的自建工作，也可能增加学习、适配或许可成本；直接编写专用系统可以贴合特定作品，但后续维护由项目承担。**许可费是成本的一部分，不是总成本；没有引擎费用，也不等于没有开发费用。**

一次新需求至少应留下五项约定：受影响的状态、允许的操作、可见反馈、保存与恢复行为、验证环境。例如“增加等待选项”应明确等待是否推进时间、是否改变环境、能否中断，以及重载后如何继续。这里要求的是设计和验收信息，不是让负责人代替程序员决定每一行实现。
