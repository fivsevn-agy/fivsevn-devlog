<a id="read-project"></a>
## 1｜先按职责认识项目

阅读项目时，可以先看说明与目录，找出玩家入口、内容位置、运行程序和发布配置。它们给出整体分工，再通过具体引用关系确认文件职责。这样，你能先定位一项需求涉及的部分，再决定哪些实现需要进一步审查。

| 内容 | 主要用途 | 阅读重点 |
| --- | --- | --- |
| 项目说明 | 介绍作品、入口、许可与维护方式 | 当前有效的规则与资料入口 |
| 运行文件 | 玩家打开作品后使用的程序和资源 | 功能之间怎样连接 |
| 内容与配置 | 保存对白、对象、布局和设置 | 哪些字段会改变运行结果 |
| 源素材 | 保留可编辑的图片、模型和音频工程 | 怎样修改并重新导出 |
| 测试与检查 | 验证规定范围内的行为 | 检查条件、预期结果与未覆盖范围 |
| 发布配置 | 规定如何生成和分发成品 | 哪些文件进入成品，发布到什么位置 |
| 历史记录 | 保存旧方案和决策过程 | 与当前要求的区别及变更原因 |

以你正在做的《等足目赋格》为例，修改已有观察文字，可以先定位相应的内容和语言模块；新增一种直接操作，则还要检查输入、状态、反馈与存档。两项修改看起来可能都只增加少量文字，但涉及的系统不同，工作量也应分别估算。[8](#ref-8)

因此，项目阅读的起点是**内容在哪里、由谁处理、结果交给谁**。文件数量和目录层级可以辅助定位，实际判断仍要回到这些职责。

<a id="request"></a>
## 2｜把修改意图写成可交付需求

“优化一下”提供了方向，但实现者还需要知道希望改善哪个问题，以及哪些现有行为应保留。把这些条件写清楚，就能在方案比较和验收时使用同一套依据。

| 项目 | 需要明确的内容 |
| --- | --- |
| 目的 | 当前问题及希望改善的体验 |
| 修改范围 | 涉及哪些页面、角色、资源或功能 |
| 保留范围 | 哪些外观、行为、存档和公开入口继续保持 |
| 预期结果 | 正常操作后出现的具体变化 |
| 边界情况 | 连续操作、中断、失败和重载时怎样处理 |
| 验收环境 | 需要检查的设备、屏幕、语言与平台 |
| 交付证据 | 修改说明、差异、检查记录和发布状态 |

例如，为你的游戏增加一条观察选项，可以约定：只修改指定生境；选择后记录结果并显示反馈；重载后继续保留结果；目标语言和手机布局中都能正常使用。这些要求先规定结果，实现者再据此安排程序结构。

**需求说明目标，技术方案说明实现方法，验收标准说明判断方式。** 若某种文件格式或旧存档必须兼容，就把它写成约束；其余内部细节可以留给实现者选择，以便在满足目标的前提下比较方案。

<a id="change"></a>
## 3｜修改、提交、分支与审查

项目会不断变化，因此需要保存可以定位的新旧版本。Git 用于记录这些修改，GitHub 等平台则围绕版本记录提供托管、讨论与审查功能。[1](#ref-1)

| 名词 | 解释 |
| --- | --- |
| 差异／Diff | 新旧版本之间增加、删除或改动的内容 |
| 提交／Commit | 一组可以定位的修改记录 |
| 分支／Branch | 相对独立的修改路线 |
| 合并／Merge | 将一条路线的修改整合到另一条路线 |
| PR／Pull Request | 提出、讨论和审查待合并修改的协作记录 |
| 标签／Tag | 为某个版本设置便于识别的名称 |

审查可以分层进行。你先核对改动是否符合约定范围、是否包含必要内容，以及验证是否充分；具备相关能力的审查者再检查代码、资源和结构细节。这样，设计判断与技术检查各有负责的部分。

如果一轮修改同时包含修复按钮、调整视觉、移动目录和升级组件，问题出现时就更难定位原因。因而，可以把变更按目的拆开，并为新增工作说明理由，使每一组修改都有清楚的验收对象。

提交记录了哪些文件发生变化，合并把变化接入目标分支，审查记录则说明哪些内容经过检查。这些步骤完成的是项目文件的管理；玩家使用的成品还需要经过构建、部署和运行验证。**因此，要确认玩家已经取得正确版本，还需继续核对发布结果与实际入口。**

<a id="verification"></a>
## 4｜理解测试结果及其范围

每项测试都在规定条件下检查某种结果。只有知道它测试了哪个版本、采用什么环境、覆盖哪些行为，才可以据此判断质量。自动化能够反复执行已经安排的检查，而范围以外的问题还需要其他验证方式补充。[2](#ref-2), [4](#ref-4)

| 检查 | 主要提供的证据 | 还需配合的检查 |
| --- | --- | --- |
| 文件与结构检查 | 引用、数据字段和目录符合约定 | 实际运行和体验 |
| 规则测试 | 指定输入与状态得到预期结果 | 界面显示及真实操作 |
| 集成检查 | 多个部分能够共同工作 | 更广的边界条件和设备环境 |
| 浏览器或设备测试 | 在指定环境完成完整操作链 | 其他目标设备与实际玩家使用 |
| 视觉比较 | 相对指定参考版本发生哪些画面变化 | 语义、资料与规则判断 |
| 试玩 | 理解、节奏和操作感受 | 程序与数据的可重复检查 |
| 无障碍检查 | 文字、输入、声音和运动等方面的可用性 | 按目标用户和平台继续验证 |

例如，网页在模拟手机视口中通过检查，说明相应尺寸与模拟输入下的表现成立；真实手机还可能有不同的系统、触摸和性能条件，因此真机检查应另行记录。无障碍也是相似的关系：指南帮助列出方向，实际用户和设备检查进一步确认可用性。[3](#ref-3), [8](#ref-8)

### 把问题记录到能够复现

**《Factorio》的开发记录解释了复现信息的价值。** 团队在讨论多人失步时提到，系统报告能够帮助比较两端状态，而玩家做了什么、在什么情况下发生问题，也会影响调查效率。[10](#ref-10) 因此，提交问题时应同时保存机器记录和操作情境，使调查者能够沿着原过程查找原因。

一份缺陷记录可以包含环境、版本、前提、步骤、预期结果、实际结果和证据。现象与原因推测应分别写：例如先记录“重载后按钮不可用”，再标注“可能与进度恢复有关”，这样后续调查可以验证推测，而不会把它误当作已经确认的结论。

交付报告也可以分别写明已经执行并通过、执行失败、尚未执行和不适用。保留这些状态，才能看出当前还缺少哪一类证据。

<a id="release"></a>
## 5｜从构建到公开版本

发布过程中，各环节的成功结果不同，可以按下面的顺序理解。

| 状态 | 准确含义 |
| --- | --- |
| 实现完成 | 所需文件或程序修改已经产生 |
| 验证通过 | 对指定版本执行的相应检查通过 |
| 已提交或合并 | 修改进入可以追踪的版本记录 |
| 构建成功 | 流程生成了成品文件 |
| 部署成功 | 成品放入目标运行环境 |
| 公开核对完成 | 从玩家实际入口检查可访问性与预期内容 |

**《Baldur’s Gate 3》的 Hotfix 4 复盘说明，测试对象与发布对象必须对应。** Larian 介绍，候选版本经过测试，但临近发布时重新构建的版本出现问题；回退又使部分新版本存档暂时无法使用。[5](#ref-5) 这意味着两项工作都需要安排：一是检查实际准备发布的文件，二是确认回退时怎样处理玩家数据（案例发生于 2023 年，修正版本随后重新发布）。

因此，候选版一旦完成验证，后续重新构建或调整资源时，就应判断哪些检查需要再次执行。回退也应同时考虑程序和数据，确认旧程序能否读取玩家已经产生的记录。

商店发行还要处理平台材料。Steam 分别审核商店页面与游戏构建，因为前者向玩家说明产品，后者提供实际体验。[6](#ref-6) 项目可以将这两项工作并行准备，再在发布前核对描述与成品是否一致。

网页排查也应逐步进行：先确认访问地址和部署版本，再检查资源是否来自同一版，最后判断缓存影响。由于网站数据中可能包含本地存档，清除数据前应先确认需要保留的进度，并尽可能导出备份。[7](#ref-7)

<a id="isopoda"></a>
## 6｜对照你的游戏和博客

你的《等足目赋格》和这套博客文章都使用版本记录与自动发布，不过它们交付的内容不同，因此验收重点也不同。[8](#ref-8), [9](#ref-9)

| 项目 | 制作中的内容 | 发布处理 | 最后检查的成品 |
| --- | --- | --- | --- |
| 《等足目赋格》网页版 | 游戏代码、内容和资源 | 准备站点，处理字体和资源版本标识 | 入口、交互、显示、声音和进度恢复 |
| devlog 手册 | Markdown 正文与文章信息 | 更新目录，将文章生成网页并部署 | 标题、顺序、表格、引用和跳转 |

游戏的普通自动检查与浏览器回归各有范围；比较新旧画面时，还需要明确使用哪个版本作为参照。[8](#ref-8) 博客则可以从文章源文件一路检查到公开网页，确认修改确实出现在读者看到的位置。

例如，你提出调整手册目录时，修改排序规则只是其中一步，还需要生成目录并完成网页部署。把这几步分开记录，就能明确当前是在修改规则、等待生成，还是已经完成公开显示检查。

这里使用固定版本的文档帮助你理解分工。以后进行新修改时，再以当时的文件和检查结果为准，即可避免把旧记录误当作本轮验证。

<a id="cost"></a>
## 7｜工具成本与交接记录

这些工具分别处理版本、自动检查与发行。费用形式沿用 **2026-10-13** 的资料记录，实际采购和资源额度需按官方当前方案核对。

| 工具或服务 | 开放情况 | 费用与用途 |
| --- | --- | --- |
| [Git](https://git-scm.com/about) | 开源 | 软件免费，备份与托管资源另计 |
| [GitHub](https://github.com/pricing) | 托管平台 | 免费与付费方案，权限和额度按计划区分 |
| [GitHub Actions](https://docs.github.com/en/billing/concepts/product-billing/github-actions) | 云服务，执行器等组件另有开放许可 | 按免费适用范围、执行环境和用量计费 |
| [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) | 静态托管服务 | 免费适用范围与仓库、方案条件相关 |
| [Jekyll](https://jekyllrb.com/) | 开源 | 软件免费，负责把文章等内容生成网页 |
| [Node.js](https://nodejs.org/en/about)、[Playwright](https://playwright.dev/) | 开源 | 软件免费，设备、云端执行和维护另计 |
| 浏览器开发者工具 | 随浏览器提供，许可依产品 | 通常无需单独购买，便于检查网页执行与资源加载 |
| [Steamworks](https://partner.steamgames.com/doc/gettingstarted) | 平台工具与服务 | 文档免费，发行接入和销售等费用按平台协议 |
| AI 开发辅助 | 依产品与接入方式 | 免费额度、订阅或按量计费，具体见 [002](posts-2026-umwelt-game-development-handbook-002.html#tools-25) |

交付时，可以要求开发者提供下面这些记录。它们让你能够检查成果，同时保留以后维护需要的信息。

| 记录 | 最低内容 |
| --- | --- |
| 变更说明 | 改动目的、实际范围和继续保留的部分 |
| 版本标识 | 工作起点与交付版本的位置 |
| 验证结果 | 环境、执行范围、结果及尚未覆盖的部分 |
| 发布结果 | 部署状态，以及公开入口的检查结果 |
| 已知限制 | 尚未解决的问题、影响和处理责任 |
| 恢复方案 | 上个稳定版本与玩家数据的处理方式 |

这些要求同样适用于 AI 辅助开发。代码阅读可以提供分析，实际运行可以提供行为证据；如果受环境限制只能完成前者，就应清楚记录分析范围，再安排后续验证。这样，协作者采用何种工具，都可以用同一套交付标准判断。
