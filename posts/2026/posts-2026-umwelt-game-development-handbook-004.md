制作游戏画面时，先确定希望呈现的风格，再选择资源的制作方法，最后安排它们在游戏中的显示与交互。这三个决定彼此相关，却可以有多种组合：同样的像素外观，可以逐像素绘制，也可以由三维模型转换而来。截图展示的是最终外观，因此要了解制作工具，还需要查看资源流程或开发者的说明。[1](#ref-1), [2](#ref-2)

你目前更需要判断视觉方案怎样落地，以及不同方案会增加哪些工作。因此，本篇围绕制作关系与验收展开；建模操作、软件按钮和着色器写法留作进一步实践的内容。

<a id="visual-route"></a>
## 1｜视觉风格与技术实现

| 名称 | 主要描述的对象 | 解释 |
| --- | --- | --- |
| 像素、手绘、写实、卡通 | 视觉风格 | 描述最终外观，可以通过不同工具和流程实现 |
| 二维图像 | 资源或显示形式 | 可以来自绘画、三维渲染、摄影或程序生成 |
| 三维模型 | 具有立体结构的资源 | 可以在游戏里实时显示，也可以提前用来生成图片 |
| 实时渲染 | 运行时的画面计算 | 根据当前相机、对象、材质和光照生成画面 |
| 预渲染 | 制作阶段提前计算画面 | 将结果保存为图像或视频，再由游戏调用 |
| 2.5D | 对二维与三维组合方式的概括 | 可能指二维玩法配三维画面，或二维角色置于三维场景；使用时最好补充具体含义 |

**《Cuphead》采用了手绘资源与游戏引擎配合的路线。** 团队在纸上绘制动画，再进行数字上色和整理，最后用 Unity 组织运行。由此可以分清：手绘是资源的制作方式，Unity 是接收资源并执行游戏的工具，两者处在相连的不同环节。[1](#ref-1)

**《Dead Cells》则说明，像素外观也可以从三维资源产生。** 美术作者 Thomas Vasseur 介绍，团队先制作三维角色与动作，再生成小尺寸的二维图像帧。最终画面保留像素风格，制作中却使用了三维模型的可调整性。[2](#ref-2)

因而，选择视觉路线时，需要分别说明目标外观、源资源和运行资源。把这三项写清楚，才能判断哪些工具互相替代，哪些需要配合使用。

<a id="composition"></a>
## 2｜一幅游戏画面的组成

角色、环境、光照和界面共同构成画面。为了使它们看起来属于同一个空间，需要统一比例、位置和遮挡关系；为了便于操作，还要让玩家辨认出哪些元素能够交互。实时三维进一步涉及几何、材质、光照与相机的配合。[3](#ref-3)

| 部分 | 定义与解释 | 制作时需要约定 |
| --- | --- | --- |
| 坐标与比例 | 记录位置和大小的参照 | 角色、背景与交互范围使用什么尺度 |
| 相机与视口 | 观察位置，以及屏幕显示的区域 | 允许怎样移动或缩放，哪些内容可以被裁切 |
| 图层与遮挡 | 元素的前后关系 | 角色经过物体后方时，哪些部分被遮住 |
| 材质与贴图 | 表面的表现方式及颜色、粗糙程度等信息 | 在目标光照与设备中呈现什么效果 |
| 光照与特效 | 明暗、气氛和动态提示 | 怎样突出信息，哪些效果可以减弱或关闭 |
| 界面 | 文字、菜单与操作控件 | 场景和控件怎样分配屏幕空间 |
| 碰撞与点击范围 | 供规则判断使用的区域 | 判定结果是否符合玩家对画面的理解 |

**《Heaven’s Vault》将二维角色放进三维环境。** 开发团队把手绘角色帧与立体场景组合使用，说明角色资源与场景资源可以采用不同形式，再通过位置、相机和显示方式形成统一画面。[8](#ref-8) 遇到“2.5D”这样的概括时，最好进一步说明究竟是哪一部分采用二维、哪一部分采用三维。

规则使用的碰撞区域也可以比可见轮廓简单，以减少计算和维护工作。不过，简化后的结果仍需符合操作预期，例如明显留有距离时不应频繁判定为碰撞。这里需要把视觉检查与操作检查放在一起。

对于你的竖屏作品，场景缩放、文字放大和按钮触摸范围也应分别安排。它们服务于观察与阅读等不同需求，因此适配手机时，应重新分配空间，而不是只将桌面画面整体缩小。

<a id="animation"></a>
## 3｜动画资源与动画控制

动画制作决定角色怎样运动，包括姿态、速度和节奏。接入游戏时，还需要规定它由什么操作触发、何时循环，以及受到打断后怎样继续。这是两项相连的工作：一段动作可以已经制作得流畅，但只有把触发与转换规则接好，玩家才能在正确时刻看见它。[4](#ref-4)

| 方式 | 内容怎样产生 | 主要取舍 |
| --- | --- | --- |
| 逐帧动画 | 连续播放一组分别制作的画面 | 便于直接控制造型与节奏；修改动作可能涉及多张图 |
| 骨骼动画 | 通过骨架带动二维部件或三维形体 | 便于复用和调整；需要制作绑定并检查变形 |
| 参数化变形 | 用参数控制图像或模型变化 | 适合连续表情和转向；可变化范围需要预先制作 |
| 程序化动画 | 根据时间、状态和规则计算变化 | 便于响应环境与交互；极端条件下的表现需要验证 |
| 动作捕捉 | 记录实际动作，再清理和映射到角色 | 可以保留表演细节；采集、清理与风格调整各有成本 |

关键帧记录重要时刻的姿态，插值再计算其中部分过渡。不过，角色的重量、力度和情绪还依赖关键姿态与时间安排。因此，即使工具能够自动生成过渡，动画制作仍需要先确定动作本身的表达。[4](#ref-4)

以你可能为鼠妇安排的触碰反应为例，可以先定义“收缩—停留—恢复”，再说明停留多久、恢复前能否再次触发，以及菜单是否仍可操作。前一部分指导动作制作，后一部分指导运行控制（这里用的是设计示例，具体行为需结合你选定的物种和现有实现）。

**动画资源负责呈现运动，游戏规则负责调用、衔接和中断这些运动。** 两部分越早一起确认，后续为了交互返工的范围就越容易控制。

<a id="pipeline"></a>
## 4｜从源文件到游戏内资源

视觉方案需要经过制作、导出和接入，才能成为玩家实际看到的内容。可以先用“视觉约定—小样—正式资源—导出—接入—检查”理解这条流程；项目简单时，几个步骤可以在同一工具中完成。

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| 视觉约定 | 比例、色彩、构图与参考说明 | 每份参考支持哪些具体特征 |
| 小样 | 一个角色、一段动作或一处场景 | 放进目标画面后能否满足需要 |
| 源资源 | 可继续修改的绘图或三维工程 | 图层、对象、命名和引用能否支持后续编辑 |
| 导出资源 | 图片、模型、动作或音频等文件 | 尺寸、透明、方向、循环与格式符合约定 |
| 游戏接入 | 将资源与状态、输入和显示连接 | 触发、遮挡、缩放、暂停和恢复正常 |
| 发布检查 | 玩家实际取得的版本 | 压缩、路径、字体与设备差异没有破坏预期表现 |

源软件与运行环境能够处理的内容可能不同，因此导出时需要约定保留哪些信息。以 glTF 为例，它提供三维资源交付格式，但具体支持哪些材质或扩展，还取决于导出器与运行端的实现。选定格式后，仍需用目标项目试着接入一份资源。[5](#ref-5)

一份简要规格可以记录名称、用途、目标画面、尺寸或比例、透明背景、定位基准、动作时长、循环方式、格式与署名要求。二维图片只需填写与自身有关的项目，三维资源再补充模型与材质条件。

因此，**源文件保留编辑能力，导出文件适合交换和运行，接入工作使资源参与游戏行为。** 验收也应沿着这条关系检查，既保存可以继续修改的源工程，也检查真正交给玩家的成品。

<a id="budget"></a>
## 5｜制作预算、运行预算与视觉验收

视觉预算包括金钱和制作时间，也包括资源体积、内存与设备性能。新增一个角色时，可能需要同时补充动作、遮挡、界面说明和测试，因此应按完整交付估算，而不只计算一张立绘的价格。

| 成本 | 常见影响因素 | 判断方式 |
| --- | --- | --- |
| 制作时间 | 角色、动作数量和修改频率 | 先完成代表性小样，再估算批量工作 |
| 资源体积 | 图像尺寸、帧数、音频和模型内容 | 按实际显示需要选择规格 |
| 运行负担 | 可见对象、特效、材质和更新频率 | 在约定设备上测量和观察 |
| 维护成本 | 源文件、工具依赖与复用结构 | 保留可编辑资源和明确的导出流程 |
| 授权成本 | 软件、插件、素材和运行组件 | 分别记录各项使用条件 |

前面介绍的《Dead Cells》管线，也可以从成本角度理解：作者重视的是反复调整动作的便利，使玩法变化时仍有余地修改动画。[2](#ref-2) 对你同样需要持续试验的项目，可修改性应在选方案时考虑，而不是等全部素材完成后再处理。

反馈则需要围绕作品的体验目标安排。GDC 演讲 _Juice It or Lose It_ 通过现场演示，展示声音、运动与其他效果怎样改变简单交互的感受。[6](#ref-6) 用到你的观察作品时，可以先确认哪个行为需要更明显的提示，再选择合适的反馈强度。这样既能让操作被察觉，也能保留安静的节奏。

实际验收还应覆盖连续操作、窗口变化、暂停恢复与较低性能设备。宣传截图适合检查构图和风格；这些运行条件则需要通过游玩来检查，两类材料各自提供不同证据。

<a id="isopoda"></a>
## 6｜对照你正在做的两个方向

以《等足目赋格》为例，鼠妇的外观和姿态由参数与程序共同生成，再通过 Canvas 2D 组合到场景中。配套实验室与游戏共享部分形态和布置数据，因此调整资料与视觉规则时，还需要检查它们在不同页面中的显示。[7](#ref-7)

你为《体温调节》讨论过的则是另一条路线：在 Blender 中统一场景、相机和角色姿态，先生成二维画面，再让网页调用。两种方案的区别，在于哪些视觉工作提前完成，哪些留到游戏运行时完成（《体温调节》一栏记录的是讨论中的方案）。

| 对照 | 《等足目赋格》的实现 | 《体温调节》讨论中的方案 |
| --- | --- | --- |
| 形态来源 | 形态参数与程序绘制 | 三维源场景与角色姿态 |
| 运行画面 | 程序生成并组合二维像素 | 调用预先导出的二维画面 |
| 修改位置 | 参数、绘制和动作规则 | 源场景、相机、姿态和导出资源 |
| 共同要求 | 状态与画面正确对应 | 状态与画面正确对应 |

因此，你可以按变化需求选择制作方式：需要频繁随参数变化的部分，可以考虑程序生成；构图和姿态较固定的部分，可以考虑提前制作。无论采用哪条路线，最后都要把资源与玩家操作接起来，才能判断它是否适合这款作品。

## 7｜本篇软件与费用类型

以下保留软件开放情况和典型费用形式，便于与制作工作一起比较。费用记录日期为 **2026-10-13**；目标版本的授权和平台条件仍以官方说明为准。完整工具表见 [002](posts-2026-umwelt-game-development-handbook-002.html#cost-legend)。

| 软件或组件 | 开放情况 | 费用与注意事项 |
| --- | --- | --- |
| [Blender](https://www.blender.org/about/license/)，含 Cycles、Eevee | 开源软件与内置组件 | 软件免费，第三方素材和插件分别适用自己的许可 |
| [Krita](https://krita.org/en/)、[GIMP](https://www.gimp.org/) | 开源 | 官网软件免费，部分商店渠道可能收费 |
| [Aseprite](https://www.aseprite.org/faq/) | 源码可见，专门许可 | 官方成品付费，自行构建与再分发按条款处理 |
| [Photoshop](https://www.adobe.com/products/photoshop.html) | 专有 | 桌面完整制作主要采用订阅，试用期限另看 |
| [3ds Max](https://www.autodesk.com/products/3ds-max/overview) | 专有 | 商业使用采用付费方案，教育资格的适用用途另行确认 |
| [Live2D Cubism](https://www.live2d.com/en/cubism/comparison/) | 编辑器专有，SDK 按专门许可 | 有受限免费版与付费版，运行集成条件另看 |
| [Spine](https://esotericsoftware.com/spine-purchase) | 编辑器与运行组件适用相应许可 | 编辑器付费，正式导出与游戏集成需满足使用条件 |
| [Unity](https://unity.com/products) | 专有 | 条件免费与付费席位方案并存 |
| Canvas 2D、glTF | 网页接口／资源格式 | 标准本身没有制作软件购买费，具体工具和平台另计 |

制作工具、运行组件和资源内容可能来自不同提供者，所以预算与授权也要分别记录。外包时，还应约定交付源文件、修改轮次和允许的使用范围，以便以后继续制作和维护。

## 参考文献与学习资源

制作案例采用开发者文章、官方访谈与作品说明；进一步学习则以动画教材、图形学教材和作者课程为主。可先看案例，再按具体问题选择读物（网页查阅日期：2026-10-13）。

<a id="ref-1"></a>
**[1] Unity／Studio MDHR. _Cuphead — Made with Unity_.** [英文访谈](https://unity.com/made-with-unity/cuphead)。免费。阅读手绘资源进入引擎的过程，比较美术生产与游戏运行的职责。

<a id="ref-2"></a>
**[2] Vasseur, Thomas. _Art Design Deep Dive: Using a 3D Pipeline for 2D Animation in Dead Cells_（2018-01-25）.** [作者原文](https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-)。英文，免费。重点看制作方法为什么适合反复调整，以及作者接受了哪些视觉取舍。

<a id="ref-3"></a>
**[3] Akenine-Möller, Tomas 等. _Real-Time Rendering_，第 4 版（2018）.** [作者官网](https://www.realtimerendering.com/)。英文，书籍购买或借阅，部分配套材料免费。先看渲染流程与图像示例；涉及算法的章节适合以后按需查阅。

<a id="ref-4"></a>
**[4] Williams, Richard. _The Animator’s Survival Kit_，扩充版（2009）.** [出版社入口](https://www.faber.co.uk/product/9780571238347-the-animators-survival-kit/)。英文，书籍购买或借阅。重点是姿态、时间和运动观察，适合用来判断动画表达。

<a id="ref-5"></a>
