画面制作至少包含三项决定：**采用什么视觉风格，以什么方式制作资源，以及游戏运行时怎样显示和控制这些资源。** 它们可以分别选择，不能只根据截图反推制作工具。

<a id="visual-route"></a>
## 1｜视觉风格与技术实现

| 名称 | 主要描述的对象 | 解释 |
| --- | --- | --- |
| 像素、手绘、写实、卡通 | 视觉风格 | 描述最终外观，不直接说明由哪种软件制作 |
| 二维图像 | 资源或显示形式 | 可以来自手绘、三维渲染、摄影或程序生成 |
| 三维模型 | 具有立体结构的资源 | 可以在游戏中实时显示，也可以只用于提前生成图片 |
| 实时渲染 | 运行时的画面计算 | 根据当前相机、对象、材质和光照生成画面 |
| 预渲染 | 预先计算资源 | 制作阶段生成图像或视频，游戏再调用成品 |
| 2.5D | 需要结合语境判断的说法 | 可能指二维玩法配三维画面、固定视角的立体场景等，并非一种统一格式 |

**《Cuphead》案例。** Unity 的制作访谈介绍了纸上绘制、扫描与数字处理动画，再接入游戏的流程。[1](#ref-1) 因此，手绘描述资源的制作与视觉风格，Unity 描述游戏的组织和运行工具，两者并不冲突。

**《Dead Cells》案例。** 美术 Thomas Vasseur 介绍了先制作三维角色和动作，再通过专用处理生成低分辨率图像帧的流程。[2](#ref-2) 最终是像素风格，不代表所有角色动作都逐像素手绘。

以上是有来源的具体制作案例，不应推广为“某种画风一定由某个软件制作”。**风格规定看起来怎样，制作路线规定内容怎样产生，运行路线规定成品怎样被使用。**

<a id="composition"></a>
## 2｜一幅游戏画面的组成

画面不是简单把所有素材叠在一起。不同元素需要共享坐标、比例和遮挡关系，玩家需要区分可操作对象、环境装饰和界面。实时三维中的几何、材质、光照与相机也是不同职责。[3](#ref-3)

| 部分 | 定义与解释 | 制作时需要约定 |
| --- | --- | --- |
| 坐标与比例 | 记录物体位置和大小的参照 | 角色、背景与交互范围是否使用一致尺度 |
| 相机与视口 | 决定观察位置及显示区域 | 玩家能否移动视角，缩放后裁切哪些内容 |
| 图层与遮挡 | 决定元素的前后关系 | 角色走到树后时，哪些部分应被挡住 |
| 材质与贴图 | 决定表面表现，并提供颜色、粗糙程度等信息 | 在目标显示环境中是否仍符合预期 |
| 光照与特效 | 形成明暗、气氛和动态提示 | 是否影响目标辨认，是否需要弱化选项 |
| 界面 | 显示文字、菜单和操作控件 | 是否与场景抢占空间，窄屏上能否操作 |
| 碰撞与点击范围 | 用于规则判断的区域 | 是否与玩家对画面的理解一致 |

可见形状与碰撞形状不一定完全一致。复杂轮廓可以用较简单的规则区域近似，但不能让玩家频繁遇到“明显没碰到却被判定碰到”的结果。

画面缩放也有不同目的。放大场景、放大文字、扩大按钮触摸范围并不是同一项操作。对竖屏作品，应单独确认场景可见范围与界面可读性，而不是将整张桌面画面一起缩小。

<a id="animation"></a>
## 3｜动画资源与动画控制

动画制作决定姿态和运动的表现，动画控制决定某段表现何时开始、结束、循环或被打断。动作画得流畅，不代表已经正确接入玩法。[4](#ref-4)

| 方式 | 内容怎样产生 | 主要取舍 |
| --- | --- | --- |
| 逐帧动画 | 连续播放一组分别制作的画面 | 造型与节奏控制直接；新增动作或改画可能增加资源量 |
| 骨骼动画 | 控制骨架，再带动二维部件或三维形体 | 有利于复用和调整；需要绑定，变形范围有边界 |
| 参数化变形 | 用参数控制图像或模型的变化 | 适合表情、转向等连续变化；参数能力需要提前制作 |
| 程序化动画 | 根据时间、状态和规则计算变化 | 可随环境与交互变化；规则和极端情况需要验证 |
| 动作捕捉 | 记录实际动作，再清理和映射到角色 | 可提供表演基础；设备、数据清理和风格适配仍有成本 |

关键帧记录重要时刻的姿态；插值计算部分中间变化。自动补出中间帧，不保证动作的力度、重量和节奏自然。动画原理教材因此仍重视姿态、时间安排与观察，而非只介绍软件功能。[4](#ref-4)

以下是一份演示性动作约定：角色受到触碰后先收缩，再停留，最后恢复；恢复前不能再次完整触发同一动作，但仍可以打开菜单。这里包含造型、时长、中断、重复输入和界面行为，不能只交付一段视频便认为功能完成。

**动画资源负责动作如何表现，游戏规则负责何时调用和中断动作。** 两者应在制作早期共同确认，否则后期可能需要重做大量已经完成的帧或绑定。

<a id="pipeline"></a>
## 4｜从源文件到游戏内资源

一种常见流程是：**视觉约定 → 小样验证 → 正式制作 → 导出与加工 → 游戏接入 → 实际检查**。它不要求每一步使用不同软件，也不要求所有项目都经过三维建模。

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| 视觉约定 | 比例、色彩、构图与参考说明 | 参考用于哪些特征，哪些特征不采用 |
| 小样 | 一名角色、一段动作或一处场景 | 放进目标画面后是否成立，而非单独展示时好看 |
| 源资源 | 可继续修改的绘图或三维工程 | 图层、对象、命名和引用是否足以继续维护 |
| 导出资源 | 图片、模型、动作或音频等成品 | 尺寸、透明、方向、循环与格式是否符合项目约定 |
| 游戏接入 | 资源与状态、输入和显示系统的连接 | 触发、遮挡、缩放、暂停和恢复是否正确 |
| 发布检查 | 玩家实际取得的版本 | 压缩、路径、字体与设备差异是否改变效果 |

资源格式不能代替完整的交付约定。即使都使用 glTF，不同导出器、导入器和扩展的支持范围也可能不同；源软件中的所有材质或控制结构，不一定自动转移到目标运行环境。[5](#ref-5)

一份简要规格可以记录：资源名称、用途、目标画面、尺寸或比例、透明背景、定位基准、动作时长与循环方式、文件格式、授权与署名、验收版本。对不涉及三维的项目，删除无关字段即可。

**源文件保留修改能力，导出文件适合交换或运行，接入步骤使资源参与游戏行为。** 三者不能互相替代。

<a id="budget"></a>
## 5｜制作预算、运行预算与视觉验收

这里的“预算”不仅指购买软件的金额，也指时间、文件体积、内存和设备能力。增加一种角色外观，可能同时增加动作、遮挡、语言说明和测试工作；其成本不能只按一张立绘估算。

| 成本 | 常见影响因素 | 适合采用的判断方式 |
| --- | --- | --- |
| 制作时间 | 角色数量、动作数量、修改频率 | 先做代表性小样，再估算批量生产 |
| 资源体积 | 图像尺寸、帧数、音频与模型内容 | 按实际显示需求选择规格，避免全部使用最大文件 |
| 运行负担 | 可见对象、特效、材质、更新频率 | 在目标设备上测量，而不是只看工作电脑 |
| 维护成本 | 源文件完整性、工具依赖、复用结构 | 保留可编辑源资源和明确的导出方式 |
| 授权成本 | 软件、插件、素材与运行组件 | 分开记录各自的许可范围 |

**《Dead Cells》带来的制作判断。** 作者强调其管线的重要收益之一是便于调整动作、应对返工，而不是单纯追求一次输出的细节上限。[2](#ref-2) 对需要频繁试验节奏的项目，可修改性本身就是视觉方案的一部分。这个启示不意味着其他作品都应复制它的三维流程。

视觉打磨需要服务于信息。GDC 演讲 _Juice It or Lose It_ 演示了动画、声音和反馈如何改变简单交互的感受。[6](#ref-6) 将它用于安静的观察作品时，应选择需要的反馈，而不是机械叠加震屏、闪光和粒子。**反馈的目标是清楚表达行为结果，并不等于效果数量越多越好。**

验收至少覆盖正常画面、快速连续操作、缩放或窗口变化、暂停与恢复、较低性能设备，以及文字和关键对象的辨认。宣传截图不能替代这些运行检查。

<a id="isopoda"></a>
## 6｜《等足目赋格》与预渲染方案的对照

《等足目赋格》的已核对版本通过参数与程序计算鼠妇像素和姿态，再由 Canvas 2D 组合场景；配套实验室共享形态和布置数据。[7](#ref-7) 这里的“模型”可以是程序组织的形态数据，不必是三维建模软件输出的网格。

此前讨论的《体温调节》则提出另一种方案：在 Blender 中统一场景、相机和姿态，导出二维画面供游戏调用。**这是拟采用的制作方案，不是对《等足目赋格》当前资源流程的描述。**

| 对照 | 《等足目赋格》已核对实现 | 《体温调节》讨论中的方案 |
| --- | --- | --- |
| 形态来源 | 形态参数与程序绘制 | 三维源场景与角色姿态 |
| 运行画面 | 程序生成并组合二维像素 | 调用预先导出的二维画面 |
| 修改位置 | 参数、绘制和动作规则 | 源场景、相机、姿态及导出资源 |
| 共同要求 | 状态与画面正确对应 | 状态与画面正确对应 |

因此，前者把部分视觉生产放在运行程序中，后者把部分视觉生产提前放在源场景制作中。两条路线都需要检查比例、动作和交互，不存在仅凭“用了三维”就必然更高级的关系。

<a id="cost"></a>
## 7｜本篇软件与费用类型

标注日期：**2026-10-13**。链接为官方入口，费用表示典型使用方式而非报价；完整对照见 [002](posts-2026-umwelt-game-development-handbook-002.html#cost-legend)。

| 软件或组件 | 开放情况 | 费用与注意事项 |
| --- | --- | --- |
| [Blender](https://www.blender.org/about/license/)，含 Cycles、Eevee | 开源软件与内置渲染组件 | 软件免费；商业使用软件与所用第三方素材许可分开判断 |
| [Krita](https://krita.org/en/)、[GIMP](https://www.gimp.org/) | 开源 | 官网软件免费；部分商店渠道可另收费 |
| [Aseprite](https://www.aseprite.org/faq/) | 源码可见，非一般开源许可 | 官方成品付费；自行构建有相应条款，不能将源码可见理解为任意再分发 |
| [Photoshop](https://www.adobe.com/products/photoshop.html) | 专有软件 | 桌面完整制作主要采用订阅；免费试用不等于长期免费许可 |
| [3ds Max](https://www.autodesk.com/products/3ds-max/overview) | 专有软件 | 商业使用主要为订阅或厂商适用方案；教育资格不能替代商业授权 |
| [Live2D Cubism](https://www.live2d.com/en/cubism/comparison/) | 编辑器专有；SDK 按专门许可 | 有受限免费版与付费版；游戏发布涉及的 SDK 许可另核对 |
| [Spine](https://esotericsoftware.com/spine-purchase) | 编辑器专有；运行组件为专门许可 | 编辑器付费，运行集成遵循其许可；试用不等于可正式导出 |
| [Unity](https://unity.com/products) | 专有软件 | 条件免费与付费席位方案；案例使用它不构成对本项目的采购建议 |
| Canvas 2D、glTF | 接口／资源格式 | 不是单独购买的游戏编辑器；具体工具、素材及平台费用另计 |

购买动画编辑器与取得运行集成许可可能是两件事；外包交付的源文件和素材授权也需要单独明确。没有采购以上软件的项目，可以采用程序化制作或其他路线，但仍需承担相应制作和维护工作。

## 参考文献与学习资源

本篇的游戏制作事实来自开发者或工具厂商访谈；管线取舍与验收表是针对制作管理的综合说明。资源不要求全部读完。网页查阅日期：**2026-10-13**。
